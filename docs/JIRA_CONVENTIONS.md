- 프로젝트: `S15P31A504`
- [Jira 보드](https://ssafy.atlassian.net/jira/software/c/projects/S15P31A504/boards/16613/backlog)

## 1. 기본 원칙

- 개발·설정 작업을 시작하기 전에 Jira 이슈를 생성합니다.
- 이슈 하나는 각각 검토 가능한 작은 작업 하나로 작성합니다. 가능하면 1~2일 안에 완료할 수 있는 크기로 나눕니다.
- 담당자는 한 명으로 지정합니다. 공동 작업자는 설명에 기록합니다.
- 제목은 무엇을 구현하거나 변경하는지 구체적으로 작성합니다.
- 모든 이슈에 작업 범위와 완료 조건을 작성합니다.
- 비밀번호, SSH 개인 키, 토큰, 환경변수의 비밀 값은 Jira에 기록하지 않습니다.

## 2. 이슈 유형

| 유형 | 용도 | 예시 |
|---|---|---|
| Epic | 여러 작업을 묶는 큰 목표 | 회원 인증, 서비스 배포 환경 구축 |
| Story | 사용자 관점의 기능 | 사용자는 로그인할 수 있다 |
| Task(작업) | 구현·설정·문서화 등 개별 작업 | 로그인 API 구현, GitLab CI 구성 |
| Bug | 오류 수정 | 만료된 토큰 요청 시 500 오류 발생 |
| Sub-task(하위 작업) | 상위 이슈 내부의 세부 작업 | API 구현에 필요한 세부 작업 |

Story와 Task는 같은 수준의 이슈입니다. 관련 Story·Task·Bug를 Epic 아래에 연결합니다. Sub-task는 필요한 경우에만 사용합니다.

아직 정해지지 않은 기능이나 기술을 확정된 내용처럼 작성하지 않습니다. 결정이 필요한 사항은 별도 Task로 관리하고, 결정 후 관련 이슈를 수정합니다.

## 3. 이슈 작성 템플릿

```markdown
## 목적
- 이 작업이 필요한 이유:

## 작업 범위
-

## 완료 조건
- 결과를 확인할 수 있는 구체적인 조건:

## 의존성 및 미정 사항
- 선행 작업 또는 팀 결정이 필요한 사항:

## 검증 기록
- 수행한 빌드·테스트 및 결과:
- 미검증 항목과 사유:
- MR 또는 결과물 링크:
```

Bug에는 재현 순서, 기대 결과, 실제 결과, 발생 환경을 추가합니다. 코드 변경이 없는 작업은 문서·설정 결과 등으로 완료 조건을 검증합니다.

## 4. 상태와 검토 운영

현재 적용된 워크플로는 다음과 같습니다.

```text
해야 할 일 → 진행 중 → 완료
```

| 상태 | 기준 |
|---|---|
| 해야 할 일 | 작업 범위와 완료 조건을 작성했지만 착수하지 않음 |
| 진행 중 | 담당자가 구현·설정·검증 중 |
| 완료 | 완료 조건을 충족하고 검증 기록을 남김. 코드 작업은 develop 병합까지 완료 |

별도의 `검토 중` 상태는 두지 않습니다. 리뷰를 기다리는 작업은 GitLab의 열린 MR 목록에서 확인합니다.

1. 작업 MR 생성 후에도 이슈는 `진행 중`으로 유지합니다.
2. 작성자가 변경 내용과 실행 결과를 확인합니다. 작성자 외 1명 리뷰를 권장하며, 승인 0명이어도 병합할 수 있습니다.
3. 병합 전에 완료 조건 충족을 확인합니다. MR 본문에 `Closes <이슈 키>`를 썼다면 `develop`에 병합될 때 `완료`로 자동 변경되고, 쓰지 않았다면 병합 후 직접 `완료`로 변경합니다.

완료는 운영 서버 배포를 뜻하지 않습니다. 배포와 배포 후 확인은 별도 Task로 관리합니다.

## 5. 스프린트 운영

- 1주 단위로 계획합니다. 기존에 생성된 주차별 스프린트를 사용합니다.
- 주 시작 시 이번 주 목표와 작업을 고르고 담당자·완료 조건·선행 작업을 확인합니다.
- 작업량과 팀 일정을 확인한 뒤 스프린트를 시작합니다.
- 매일 진행 상황과 막힌 일을 짧게 확인하고 Jira를 갱신합니다.
- 주 종료 시 완료 조건을 확인하고 미완료 작업의 사유와 다음 계획을 기록합니다.
- 스프린트 배정은 계획이며, 실제 착수·완료 상태를 대신하지 않습니다.
- 예상 기간이나 Story Points는 팀 합의 후 입력합니다. 초기 등록 이슈에는 임의의 점수를 넣지 않았습니다.

현재 1주차(2026-10-06~10-12), 2주차(2026-10-12~10-19) 스프린트가 생성되어 있습니다. 이후 일정은 팀 계획에 맞춰 조정합니다.

## 6. Git 브랜치·커밋·MR 연결

1. Jira 이슈를 생성하고 착수 시 `진행 중`으로 변경합니다.
2. 최신 `develop`을 기준으로 Jira의 브랜치 생성 규칙에 맞춰 작업 브랜치를 생성합니다.
3. 커밋 및 MR 제목에 해당 Jira 이슈 키를 넣습니다.
4. 작업 MR 대상 브랜치는 `develop`으로 지정합니다. MR 링크는 GitLab이 Jira 이슈에 자동으로 남깁니다.
5. 이 MR로 이슈가 끝나면 MR 본문에 `Closes <이슈 키>`를 씁니다.
6. 검증·Squash 병합 후 `Closes`를 쓰지 않았다면 `완료` 처리를 직접 합니다.

브랜치 이름 예시:

```text
S15P31A504-6-ci-build-test
```

실제 브랜치 이름은 Jira 생성 규칙을 따르며, 예시의 작업명은 참고용입니다.

커밋 및 MR 제목 예시:

```text
chore: CI 빌드·테스트 파이프라인 구성 [S15P31A504-6]
```

- GitLab 기본 브랜치는 `develop`입니다. 작업 MR의 대상은 `develop`, 배포 MR의 대상은 `main`인지 확인합니다.
- `develop → main` 배포 MR은 Squash와 소스 브랜치 삭제를 해제합니다.

### GitLab ↔ Jira 연동

GitLab 프로젝트의 Jira 연동(Settings → Integrations → Jira)을 2026-10-16에 설정했습니다.

| 하는 일 | 방법 |
|---|---|
| Jira 이슈에 커밋 · MR 링크와 댓글 남기기 | 커밋 메시지나 MR 제목 · 본문에 이슈 키(`S15P31A504-139`)를 씁니다 |
| GitLab 화면의 이슈 키를 Jira 링크로 표시 | 자동 |
| Jira 이슈를 `완료`로 변경 | MR 본문에 `Closes S15P31A504-139`를 쓰고 `develop`에 병합합니다. `Fixes`, `Resolves`도 같습니다 |

- 이슈의 일부만 끝내는 MR에는 `Closes` 없이 이슈 키만 씁니다. `Closes`를 쓰면 병합하는 순간 `완료`가 되므로 병합 전에 완료 조건을 확인합니다.
- 자동 댓글은 연동 설정에 API 토큰을 등록한 팀원 이름으로 남습니다. 토큰이 만료되거나 삭제되면 연동이 멈추므로, 그 팀원이 토큰을 다시 만들어 GitLab 설정에 넣습니다. 토큰 값은 Jira · 저장소 · 메신저에 남기지 않습니다.
- Jira 이슈 화면의 개발 패널(브랜치 · 커밋 · MR 목록)은 Jira 관리자의 앱 설치가 필요해 설정하지 않았습니다.

## 7. 라벨과 빠른 필터

| 라벨 / 필터 | 용도 |
|---|---|
| `infra` / 인프라 | 서버·배포·CI/CD 작업 |
| 나에게 할당 | 현재 사용자에게 배정된 작업. 기존 필터 |
| 최근 업데이트됨 | 최근 1일 내 변경된 작업. 기존 필터 |

필터 쿼리:

```jql
labels = infra
```

새 라벨은 같은 의미의 이름이 중복되지 않도록 팀에서 합의 후 추가합니다.

## 8. 의존성과 변경 사항

- 선행 작업이 필요한 경우 관련 이슈를 연결하고 설명에 대기 사유를 작성합니다.
- 진행이 막히면 현재 상태를 유지하면서 필요한 결정·지원·선행 작업을 기록하고 팀의 일일 확인 때 공유합니다.
- 작업 범위가 크게 달라지면 이슈 설명과 완료 조건을 갱신합니다. 별도로 검토 가능한 작업은 새 이슈로 분리합니다.
- 버그나 추가 요청은 새 이슈로 등록하고 관련 기존 이슈·MR을 연결합니다.
