# Git 협업 규칙

6명으로 구성된 팀이 약 8주 동안 진행하는 프로젝트의 Git 협업 규칙입니다. [GitLab 프로젝트](https://lab.ssafy.com/s15-final/S15P31A504)는 `S15P31A504`이며, 작업은 Jira로 관리합니다.

## 1. 브랜치 운영

| 브랜치 | 역할 |
|---|---|
| `main` | 통합 검증을 마친 배포·시연용 코드 |
| `develop` | 기능을 모으고 통합 테스트하는 코드 |
| 작업 브랜치 | Jira 작업별 개발 코드 |

- 기본 브랜치는 `develop`이며, 상시 운영 브랜치는 `main`과 `develop`입니다. `master`는 사용하지 않습니다.
- 작업 브랜치는 최신 `develop`에서 생성합니다.
- 로그인 API, 로그인 화면처럼 각각 검토 가능한 작은 작업 단위로 나눕니다.
- 작업 완료 후 MR(Merge Request)을 통해 `develop`에 병합합니다.
- `develop`은 배포·시연 전 통합 검증을 마친 뒤 MR로 `main`에 반영합니다.

## 2. 브랜치 이름

Jira의 브랜치 생성 규칙을 따릅니다.

```text
<Jira 이슈 키>-<작업명>
```

다른 프로젝트의 예시:

```text
S15P21A207-313-mcp-qa5
```

이번 프로젝트에서는 실제 Jira 이슈 키를 사용합니다. 브랜치 생성 시 기준 브랜치가 `develop`인지 확인합니다.

## 3. 커밋 메시지

```text
<타입>: <한글 설명> [<Jira 이슈 키>]
```

예시의 `PROJECT-123`은 실제 Jira 이슈 키로 바꿉니다.

```text
feat: 로그인 API 구현 [PROJECT-123]
fix: 로그인 토큰 만료 처리 수정 [PROJECT-124]
```

| 타입 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 오류 수정 |
| `refactor` | 동작을 유지하면서 코드 구조 개선 |
| `style` | 공백·들여쓰기·포맷 변경 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 작성·수정 |
| `chore` | 의존성·설정·빌드 등 기타 작업 |

- 의미 있는 변경 단위로 커밋합니다.
- 서로 다른 목적의 변경은 가능한 한 커밋을 나눕니다.
- 설명에는 무엇을 변경했는지 구체적으로 작성합니다.

## 4. MR과 병합

- 리뷰 승인은 필수가 아니며, 작성자 외 1명 리뷰를 권장합니다.
- 리뷰 없이 병합하더라도 작성자가 변경 내용과 실행 결과를 확인합니다.
- 작업 브랜치 → `develop`은 Squash 병합합니다.
- `develop` → `main`은 Squash를 해제하고 Merge commit 방식으로 병합하여 두 브랜치의 커밋 이력을 연결합니다. `develop`은 삭제하지 않습니다.
- GitLab의 Squash 설정은 `Encourage`로 적용하여 MR 생성 시 기본 선택됩니다. 작업 MR에서는 유지하고, 배포 MR에서는 해제합니다.
- Squash 결과의 커밋 메시지도 위 커밋 규칙을 따릅니다.
- 병합이 완료된 작업 브랜치는 삭제합니다.
- MR 제목도 커밋 메시지와 같은 형식을 사용합니다.
- MR 본문은 템플릿을 따라 Jira 이슈, 변경 내용, 확인한 빌드·테스트 결과와 미검증 항목을 작성합니다.
- MR 템플릿의 체크박스 항목은 해당 여부와 무관하게 모두 보존합니다. 실제로 수행·확인한 항목만 체크하고, 미검증·해당 없는 항목은 체크하지 않은 채 사유를 적습니다. 작업 MR의 Squash와 소스 브랜치 삭제 옵션도 유지합니다.

### MR 본문 템플릿

템플릿은 [.gitlab/merge_request_templates/Default.md](../.gitlab/merge_request_templates/Default.md)에 있습니다. GitLab에서 새 MR을 만들면 본문에 자동으로 채워집니다. 이 파일이 기본 브랜치(`develop`)에 병합된 뒤부터 적용됩니다.

## 5. 보호 규칙

- `main`, `develop`에 직접 push를 금지합니다.
- 모든 변경은 MR을 통해 반영합니다.
- `main`, `develop`에 force push를 금지합니다.

GitLab에서 두 브랜치를 보호 브랜치로 지정하고 다음 설정을 적용합니다.

| 설정 | `main` / `develop` |
|---|---|
| Allowed to merge | Developers + Maintainers |
| Allowed to push and merge | No one |
| Allowed to force push | 비활성화 |

리뷰 승인은 0명이어도 병합할 수 있도록 운영하며, 작성자 외 1명 리뷰를 권장합니다. 현재 프로젝트 설정 화면에는 필수 승인 수를 지정하는 메뉴가 제공되지 않아 별도의 승인 수 설정은 적용하지 않았습니다.

기본 브랜치는 `develop`입니다. 작업 MR 대상은 `develop`, 배포 MR 대상은 `main`인지 확인합니다. Jira 브랜치 생성 규칙과 커밋 메시지 형식은 팀원이 준수하며, 서버에서 자동 검사하도록 설정한 상태는 아닙니다.

## 6. 작업 순서

1. Jira에서 작업 이슈를 확인합니다.
2. 최신 `develop`을 기준으로 Jira 규칙에 맞는 작업 브랜치를 생성합니다.
3. 작업을 진행하고 의미 있는 변경 단위로 커밋합니다.
4. 작업 브랜치를 push하고 `develop`을 대상으로 MR을 생성합니다.
5. 변경 내용과 빌드·테스트 결과를 확인하고, 가능하면 작성자 외 1명에게 리뷰받습니다.
6. Squash 커밋 메시지를 확인한 뒤 병합하고 작업 브랜치를 삭제합니다.
7. 배포·시연 전 `develop`을 통합 검증하고 MR로 `main`에 반영합니다. 이 MR에서는 Squash와 소스 브랜치 삭제를 해제합니다.
