# 라넬 AI 인터랙티브 미디어아트 — 분산형 설계

작성일: 2026-10-19 · 배치 결정 갱신: 2026-10-21 · 단계: 기업 요청에 따른 프로토타입 제작 · 개정: 분산형 설계 1.4 (편집 제작: AI가 채운 명세를 운영자가 편집)

**운영 PC의 PySide6 앱이 EC2의 FastAPI에 연결하고, 동일한 제작 노드 N대가 서로 다른 작품을 병렬 제작한다. 별도 시연 노드 1대는 현재 작품을 계속 실행하면서 검증된 다음 작품을 준비·교체한다. 작품·작업·버전의 기준 상태는 PostgreSQL에 저장하며, SQLite는 초기 구성에 포함하지 않는다. 표현 템플릿은 장면 계열과 흐름 계열로 나누며, 계열에 따라 필요한 명세 항목과 작업 그래프가 달라진다.**

이 문서는 첨부안의 자유 입력·추출 근거·팔레트·자산 관리·단계별 재시도 아이디어를 기존 분산 아키텍처에 통합한 구현 설계다. 1.1 개정에서는 표현 템플릿을 두 계열로 구분하고, 계열별 명세·작업 그래프·검수·구현 순서를 추가했다. 1.2 개정에서는 계열별로 나눴던 명세 항목을 한 스키마로 합치고 계열에 따라 칸을 필수·선택·막힘으로 나눴으며, 자연어 입력을 매칭할 값 목록과 매칭 규칙을 추가했다. 1.3 개정에서는 추출·기획 결과 전체를 사람이 확인·보정한 뒤 제출하는 단계를 없애고, 입력 처리 단계(5.1)를 추가했으며, 보조 제작을 빈 칸만 묻는 편집 제작 모드로 정리했다. 목록에 없는 표현은 칸 종류와 매칭 확신도에 따라 다르게 처리하고, 못 맞춘 원문 구절을 버리지 않고 다음 단계로 넘기도록 했다(6.2). 1.4 개정에서는 빈 칸만 묻던 편집 제작을 바꿔, 두 모드 모두 AI가 명세를 먼저 채우고 편집 제작에서는 운영자가 그 명세 전체를 편집하도록 했다. 묻는 칸이 많아 운영자가 지치는 문제를 줄이기 위해서다. 운영자가 일부러 비운 칸(`"none"`)과 막힌 칸(`null`)의 표시도 정했고, 이와 겹치지 않도록 `reveal`의 "캐릭터 없음" 값을 `none`에서 `field`로 바꿨다(3.3). 장면 계열에는 2D·2.5D를 정하는 `dimension` 칸을 추가했다. 상단 이미지는 1.0 기준의 v4 ‘분산형 설계 · 도형 중심’ 페이지이며, 계열 분기는 아직 구성도에 반영하지 않았다. 기존 구성도 4개 페이지는 그대로 보존했으며, 상세 상태·계약·구현 제안은 본문을 따른다. 목표 구조를 설명하는 것이며 전체 시스템의 구현·성능 검증이 완료됐다는 뜻은 아니다.

중앙제어는 논리 서비스의 묶음이다. 서비스마다 별도 PC를 요구하지 않으며, 초기에는 제공받은 EC2에서 함께 실행할 수 있도록 구성한다. 실제 자원 배치는 부하와 제공 조건을 확인해 정한다. 운영 앱을 종료해도 중앙 작업과 Agent, 현재 전시는 계속 실행돼야 한다.

중앙제어가 수행하는 작업은 API 처리, 상태 기록, 메시지 전달, 외부 AI 호출 중계로 모두 CPU 기반 작업이다. 이미지·에셋 생성은 현장 생성 PC에서, UE 조립은 별도 제작 노드에서 처리하므로 EC2에 GPU를 요구하지 않는다. 다만 PostgreSQL·RabbitMQ·Celery·FastAPI를 한 인스턴스에서 함께 실행할 경우 메모리가 병목이 될 수 있으며, 생성 자산과 로그를 EC2 디스크에 적재하면 저장공간이 빠르게 소진된다. 실제 인스턴스 타입·볼륨 크기·증설 가능 여부를 확인하기 전까지 충분하다고 단정하지 않는다. 자산은 11장의 저장소 정책에 따라 EC2 디스크 밖에 둔다.

## 2. 장비·논리 서비스별 책임

| 위치·구분 | 구성요소 | 책임 |
|---|---|---|
| 운영 PC — 클라이언트 | PySide6 · Qt Widgets | 계열 선택, 요청 작성, 명세·진행 상황·중간 결과·전시 상태 조회, 예외 제어 |
| EC2 — 논리 서비스 | FastAPI · Head · 스케줄러 | 요청 검증, 작품 기획, 계열별 작업 그래프 생성, 의존성·예산·재시도·작업 소유권 관리 |
| EC2 — 논리 서비스 | PostgreSQL | 작품 명세·작업·시도·노드·자산 참조·검수·게시·관측 상태의 기준 기록 |
| 중앙 실행 환경 — 논리 서비스 | RabbitMQ · Celery Worker · 조립 디스패처 | 작업 전달, 외부 AI 호출·전처리·검수 조정, Windows Agent로의 작업 중계 |
| 생성·저장 영역 — 논리 서비스 | 공급자 어댑터 · AssetStore | 생성 접수·조회·회수, 원본·가공 자산·버전별 번들 저장과 전달 |
| 생성 PC 1대 — 물리 장비 | 생성 클라이언트·생성 도구·전용 공유 디스크 | 배경·에셋 생성, 공유 저장소 호스팅. 실제 생성 실행은 현재 수동 Codex이며 자동 공급자 연결은 후속 |
| UE 제작 PC 초기 2대 → N대 — 물리 장비 | 동일 Node Agent · UE Assembly Worker | 캐시·무결성 확인, 작품 조립, 모의 입력·프리뷰·기술 검증, 결과 업로드 |
| 검수·게시 영역 — 논리 서비스 | 검수기 · 중앙 게시자 | 계열별 후보 평가, 원인별 재작업, 통과 작품 자동 승인, 시연 대상 교체 직렬화 |
| 시연 PC 1대 — 물리 장비 | Show Agent · 캐시 · UE Runtime 1개 | 검증된 작품 수신·준비·교체·활성 상태 보고, 마지막 정상 작품 보존 |
| 시연 현장 | 카메라 · TouchDesigner · 전시 화면 | 손 입력 생성·전달과 실제 화면 출력 |

초기 현장 물리 장비는 **생성 1대 + UE 제작 2대 + 시연 1대 = 총 4대**다. 공유 저장소는 생성 PC가 겸하며 별도 저장 PC/NAS를 추가하지 않는다. 중앙 EC2와 제공 전의 임시 중앙 노트북은 이 현장 4대와 구분한다. 운영 앱은 기존 현장 PC에서 실행할 수 있으며 전용 운영 PC를 별도로 포함하지 않는다.

UE 제작 PC는 2대로 시작하되 동일 코드·UE/플러그인·카탈로그와 공통 작업함을 유지하며 N대로 확장한다. 노드당 조립 작업·UE 1개 제한에 따라 초기 조립 동시 실행 상한은 2개, 확장 후는 가용 제작 노드 N개다. 생성·시연 각 1대를 유지하면 현장 총대수는 N+2대다. 대기 용량과 성능 실측은 별도다.

생성·전처리 실행부는 현장 생성 PC에 배치하고 CPU/GPU·도구별 자원 요구는 따로 확인한다. 외부 AI 호출을 중계하는 서비스가 있다고 해서 일반 EC2에서 이미지 생성 모델을 직접 추론하는 것으로 표현하지 않는다. 로컬 추론은 별도 채택·자원 검증이 필요한 확장 후보이며 시연 노드에 배치하지 않는다. 현재 연결·미구현 범위는 [통신 파이프라인](../COMMUNICATION_PIPELINE.md), 실제 경로 예시는 [저장소 배치](../../infra/STORAGE.md)를 따른다.

## 3. 표현 템플릿 계열

### 3.1 두 계열의 구분

표현 템플릿은 계열을 속성으로 가진다. 계열은 작품의 최상위 타입이 아니라 템플릿의 분류이며, 같은 계열 안에 여러 템플릿이 존재할 수 있고 새 계열을 추가할 수 있다.

| 계열 | 코드 | 구성 방식 | 개별 시각 자산 |
|---|---|---|---|
| 장면 계열 | `scene_family` | 배경·객체 자산을 조립해 화면을 구성 | 필요 |
| 흐름 계열 | `flow_family` | 입자·궤적·장(field)의 거동 규칙과 파라미터로 구성 | 불필요 (배경 이미지만 선택) |

두 계열을 나누는 근거는 미학적 분류가 아니라 **작업 그래프가 달라진다는 점**이다. 장면 계열은 외부 AI 생성과 전처리를 거쳐야 조립할 수 있고, 흐름 계열은 생성 단계 없이 바로 조립한다. 흐름 계열은 원문이 배경을 요구할 때만 배경 이미지 하나를 생성한다(3.3). 이 차이가 큐 구성·의존성·검수 항목·실패 경로를 모두 바꾸므로 명세 단계에서 구분한다.

흐름 계열의 참고 사례로 관람객 움직임이 흐름을 만들고 그 흐름들이 합쳐져 소용돌이를 이루며, 사람이 멈추거나 떠나면 흐름이 사라지는 형태의 작품이 있다. 이런 작품에는 등장 캐릭터도 배경 이미지도 없고, 재생 길이가 고정되지 않는다.

### 3.2 계열 선택은 사용자가 한다

운영 UI에서 계열을 먼저 선택한다. Head의 추측에 맡기지 않는 이유는 다음과 같다.

- 계열이 틀리면 이후 명세 항목 전체가 무의미해진다. 다른 항목은 틀려도 결과가 달라지는 정도지만, 계열 오판은 작업 그래프 자체를 잘못 만든다.
- 계열을 먼저 알면 **그 계열에서 쓰는 칸만 Head에 넘겨 원문을 해석**할 수 있어 Head의 정확도가 올라간다(3.3).
- 자동 제작 모드에서도 계열은 운영 정책이 지정한다. 랜덤 운영 시 계열 비율을 정책으로 관리한다.

운영 UI의 선택지 라벨에 `scene_family`·`flow_family` 같은 내부 코드나 ‘장면 계열/흐름 계열’ 같은 분류명을 그대로 노출하지 않는다. 사용자가 판단할 수 있는 설명과 예시 이미지를 함께 제시한다.

### 3.3 명세 스키마와 계열별 칸 상태

명세 스키마는 하나다. 계열은 그 안의 칸(`template_family`) 하나이며, 계열에 따라 각 칸이 **필수 / 선택 / 막힘** 중 하나가 된다.

- **필수:** 원문에서 채워지지 않으면 Head가 반드시 채운다(두 모드 공통). 편집 제작 모드에서 운영자는 값을 바꿀 수 있지만 비울 수는 없다.
- **선택:** 원문에 근거가 있을 때만 채우고, 비어 있으면 템플릿 기본값을 쓴다(두 모드 공통). 편집 제작 모드에서 운영자는 값을 바꾸거나 `"none"`으로 일부러 비울 수 있다.
- **막힘:** Head도 운영자도 채우지 않는다. 값은 항상 `null`이며 생성 단계로 넘기지 않는다. 예를 들어 흐름 계열에서는 `main_character`가 막혀 있어, 요청하지 않은 캐릭터가 작품에 끼어들지 않는다.

생성 단계로 넘기는 명세의 칸 값은 세 가지다.

| 값 | 뜻 | 쓸 수 있는 칸 |
|---|---|---|
| 실제 값 (`"follow"`, `"풀숲"` 등) | 정해진 값 | 필수·선택 |
| `"none"` (문자열) | 편집 제작 모드에서 운영자가 **일부러 비운** 칸. 생성 단계는 이 칸을 쓰지 않고 기본값도 채우지 않는다 | 선택 칸만. 필수 칸에 넣으면 지원 규격 검사(5.1 ④)에서 거절한다 |
| `null` | **막힌** 칸. 이 계열에서 쓰지 않는다 | 막힌 칸만. 운영자가 바꿀 수 없다 |

`content.reveal`에서 "캐릭터 없이 장만"을 뜻하는 값은 `field`다. 현재 프로토타입 코드의 `Reveal.none`에 해당하지만, `"none"`(일부러 비움)과 글자가 겹치지 않도록 명세에서는 이름을 바꿨다. 명세의 `field`는 실행 값 변환(5.1 ⑧)에서 기존 코드 값으로 바꾼다. 그래서 명세의 `"none"`은 어느 칸에서든 "운영자가 일부러 비움" 하나만 뜻한다.

칸은 세 덩어리로 나눈다. **무엇이 보이나**(`content`), **아무도 없을 때**(`idle`), **사람이 오면**(`interactions`, 규칙 여러 개 가능)이다. 값 목록은 6절에 있다.

| 덩어리 | 칸 | 입력 방식 | 장면 계열 | 흐름 계열 |
|---|---|---|---|---|
| — | `template_family` 계열 | 목록 (사용자·운영 정책만) | 필수 | 필수 |
| — | `mode` 제작 모드 | 목록 `auto`·`edit` (운영 UI·운영 정책만) | 필수 | 필수 |
| — | `unmatched_phrases` 못 맞춘 구절 | 해석 결과 (원문 구절과 해당 칸) | 선택 | 선택 |
| content | `theme` 주제 | 자유 텍스트 | 필수 | 필수 |
| content | `mood` 분위기 | 자유 텍스트 | 필수 | 필수 |
| content | `palette` 색상 팔레트 | 색 목록 | 선택 | 선택 |
| content | `composition` 시점·구도 | 자유 텍스트 | 선택 | 선택 |
| content | `main_character` 메인 캐릭터 | 자유 텍스트 (수량·외형 포함) | 템플릿이 요구할 때 필수 | 막힘 |
| content | `reveal` 드러내는 방식 | 목록 | 메인 캐릭터가 있으면 필수 | 막힘 |
| content | `background` 배경 | 자유 텍스트 (캐릭터 미포함) | 필수 | 선택 |
| content | `dimension` 화면 깊이 | 목록 `2d`·`2.5d` | 필수 | 막힘 |
| content | `style` 스타일 | 목록 | 선택 | 막힘 |
| content | `material` 재질 | 자유 텍스트 | 선택 | 막힘 |
| content | `lighting` 조명 | 자유 텍스트 | 선택 | 막힘 |
| content | `medium` 매질 | 목록 | 선택 | 필수 |
| content | `density` 밀도 | 0~1 실수 | 선택 | 선택 |
| content | `influence_range` 영향 범위 | 목록 | 선택 | 선택 |

| interactions[] | `input` 입력 | 목록 | 필수 | 필수 |
| interactions[] | `reaction` 반응 | 목록 | 필수 | 필수 |
| interactions[] | `reaction_mode` 반응 방식 | 목록 | 필수 | 필수 |
| interactions[] | `return` 복귀 | 목록 | 필수 | 필수 |
| interactions[] | `duration_sec` 반응 길이 | 초 | 선택 | 막힘 |

설계 근거는 다음과 같다.

- **흐름 계열에서도 `background`를 선택 칸으로 연다.** "도시 야경 위로 비가 내린다"처럼 입자·궤적 아래에 배경 이미지가 필요한 흐름 작품이 있기 때문이다. 원문에 배경 요구가 있을 때만 채우고, 비어 있으면 배경 이미지 없이 팔레트의 배경색만 쓴다. 채워진 경우에만 배경 생성 작업이 작업 그래프에 붙는다(14절). 단색·그라데이션 배경("검은 화면")은 이미지가 아니므로 계속 `palette`에 둔다.
- **장면 계열에서도 흐름 쪽 칸을 선택으로 연다.** "수많은 물방울로 된 고래가 잔상을 남기며 사람 쪽으로 헤엄쳐 온다"처럼 캐릭터가 있으면서 입자·잔상·끌림 성질도 있는 요청을 한 명세에 담기 위해서다. `medium`·`density`·`influence_range`·`idle.motion`이 여기에 해당한다.
- **작품 전체의 재생 시간 칸을 두지 않는다.** "사람이 등장하면 풀숲에서 호랑이가 뛰쳐나온다" 같은 작품도 평상시 → 입력 → 반응 → 복귀를 반복할 뿐 정해진 길이가 없다. 모든 작품은 다음 작품이 적용될 때까지 실행한다(`display_policy: until_next_applied`). 길이가 있는 것은 반응 한 번이므로 `interactions[].duration_sec`에 둔다.
- **이전 판의 `persistence`(영속성)는 `return`(복귀)에 합쳤다.** 둘 다 반응이 끝난 뒤 흔적이 어떻게 되는지를 묻는다.
- **이전 판의 `motion_rule`(운동 규칙)은 `idle.motion`(평상시 움직임)으로 바꾸고 반응과 같은 목록을 쓴다.** 말이 거의 같고, 차이는 아무도 없을 때 움직이느냐 사람이 왔을 때 움직이느냐뿐이다. 같은 매칭 표 하나로 두 칸을 채운다.
- 이전 판의 `space`(공간감)는 `composition`(시점·구도)과 겹쳐 하나로 합쳤다. `asset_roles`(템플릿이 요구하는 자산 역할)는 원문에서 뽑는 칸이 아니라 템플릿 계약에서 정해지는 값으로 보고 이 표에서 뺐다. 두 가지는 이 개정에서 정리하며 판단한 것이므로 19절에서 확인한다.

명세 전체의 모양과 칸마다의 타입은 다음과 같다. 대문자로 시작하는 타입(`Reveal`, `Medium` 등)은 6.1의 값 목록이다. 아래 타입의 `null`은 막힌 칸이나 아직 정하지 못한 칸이고, 편집 제작에서 운영자가 일부러 비운 선택 칸은 `"none"`이다(위 표). 실제 예시는 6.4에 있다.


### 3.4 흐름 계열의 실행기 지원 — 확인 항목

흐름 계열이 현재 실행기에서 지원되거나 구현 예정이라는 점은 사용자 확인에 따른 것이며, 이 문서 작성 시점에 실행기 계약을 직접 확인한 결과는 아니다. 게시 경로에 포함하기 전에 다음을 확인한다.

- [ ] 흐름 계열 템플릿이 사용하는 UE 자산·파라미터의 실제 계약 형식
- [ ] `scene.json`에서 흐름 파라미터를 전달하는 필드 구조와 허용 범위
- [ ] 손 입력이 흐름 거동에 연결되는 경로와 TD 측 요구 데이터
- [ ] 지속 실행 시 메모리·프레임 시간·반복 교체 비용
- [ ] 입력 종료 후 복귀 동작과 무입력 상태의 기본 거동

확인 전까지 흐름 계열은 명세·작업 그래프 설계를 진행하되 게시 대상에서는 미검증으로 구분한다.

## 4. 전체 데이터 흐름과 병렬 처리

제작과 전시는 다음 두 경로로 나뉜다. 제작 경로는 계열에 따라 분기한다.

```text
작품 제작·배포
운영 요청 / 자동 운영 정책
  → 계열 선택
  → Head 기획·명세 확정 (계열에서 쓰는 칸만 해석, 3.3)
  → 계열 분기
      ├ 장면 계열
      │   → 배경 생성·준비
      │   → 배경을 참조한 시각 에셋 생성
      │   → 필요한 전처리
      │   └→ 공통 UE 조립 큐
      └ 흐름 계열
          → 파라미터 검증 (외부 생성 없음)
          └→ 공통 UE 조립 큐
  → 공통 UE 조립 큐
      ├ 제작 노드 1: 작품 A 조립·프리뷰·기술 검증
      ├ 제작 노드 2: 작품 B 조립·프리뷰·기술 검증
      └ 제작 노드 … N: 같은 기능으로 다른 작품 처리
  → 자동 검수 (계열별 항목) → 승인 번들 저장 → 중앙 게시자
  → Show Agent 다운로드·검사 → 같은 UE의 다음 작품 준비
  → Ready → 교체 → Applied 확인

시연의 실시간 입력·출력
카메라 → TouchDesigner → UE Runtime의 현재 활성 작품 → 전시 화면
```

**계열 분기는 생성·전처리 구간 한 곳이다.** 기획·조립·검수·게시·시연은 공통 경로를 사용한다. 흐름 계열은 생성 단계를 건너뛰므로 별도 파이프라인이 아니라 같은 그래프에서 노드가 비는 형태다. 조립 큐는 계열과 무관하게 공유하며, 계열별 전용 큐로 분리하지 않는다.

배경에 필요한 규격 변환은 에셋 생성 전에 전처리 큐에서 수행할 수 있다. 전처리는 한 번만 거치는 고정 단계가 아니라 필요한 자산마다 사용하는 작업 종류다. 같은 작품에서는 승인된 배경 참조가 준비된 뒤 관련 에셋을 생성한다. 서로 다른 작품은 각자의 의존성이 충족되는 대로 병행한다.

예를 들어 작품 A를 시연하는 동안 B는 노드 1에서 조립하고, C는 노드 2에서 조립하며, D는 외부 AI에서 배경을 생성할 수 있다. 각 제작 노드의 기능은 같고 배정된 작품만 다르다. 모든 제작 노드가 호환·정상·가용 상태일 때 조립 동시 실행 상한은 N개다. UE를 사용하는 별도 재검증이 있으면 그 작업도 해당 노드의 같은 실행 자리를 사용한다.

흐름 계열은 외부 공급자 호출이 없어 대기 시간과 비용이 발생하지 않고 생성 실패 경로도 없다. 다만 조립과 검수에서 UE를 사용하므로 **제작 노드의 실행 자리는 동일하게 점유한다.** 흐름 계열이라고 해서 조립 동시 실행 상한이 늘어나지 않는다.

## 5. 입력 UI와 자동 기획

기본 입력은 자유 텍스트다. 계열 선택을 제외하면 운영자가 먼저 여러 필드를 채울 필요 없이, Head가 원문을 해석하고 지원 가능한 표현·반응으로 작품 명세를 만든다. **두 모드 모두 AI가 명세의 모든 칸을 먼저 채운다.** 모드는 그다음에 사람이 손을 대는지만 다르다. 자동 제작은 AI가 채운 명세를 그대로 생성 단계로 넘긴다. 편집 제작은 AI가 채운 명세 전체를 운영자에게 보여 주고, 운영자가 원하는 칸을 고친 뒤 넘긴다. 빈 칸마다 따로 묻지 않으므로 운영자가 답할 질문이 쌓이지 않는다.

편집 제작에서 운영자가 제출하기 전까지 그 작품은 입력 대기 상태로 남고 작업을 만들지 않으며, 다른 작품의 제작과 현재 재생에는 영향이 없다. 제출하지 않을 작품은 예외 제어로 취소한다. 입력 대기 상태를 작품 상태와 명세 리비전 중 어디에 기록할지는 14절 데이터 모델에서 정한다(미정). 제출 뒤에는 기획부터 게시까지 자동으로 진행하며, 운영 화면은 명세·추출 근거·진행 상황을 조회한다. 운영 UI에서는 Shift+Tab으로 모드를 바꾸며, 명세의 `mode`에 `auto` 또는 `edit`로 기록한다.

| 모드 | 동작 | 사용 범위 |
|---|---|---|
| 자동 제작 — 기본 | 계열 결정(사용자 선택 또는 운영 정책) → 원문 해석 → 빈 칸 채우기 → 지원 규격 검사 → 작업 생성 | 모든 작품. 작품별 확인 클릭 없이 기획부터 게시까지 진행. 자동 운영 정책은 이 모드만 쓴다 |
| 편집 제작 — 선택 | 계열 선택(사용자) → 원문 해석 → 빈 칸 채우기(자동 제작과 같음) → **운영자가 명세 전체를 편집** → 지원 규격 재검사 → 작업 생성 | 원하는 값이 분명한 특정 작품, 초기 튜닝. 원문에서 뽑은 칸을 포함해 막히지 않은 모든 칸을 고칠 수 있다 |
| 예외 제어 | 작업 보류·취소·수정본 생성·재시도·교체 중지·정상 버전 복구 요청 | 실패·미지원 요구·운영상 개입 |

**편집 대상 결정 (2026-10-20, S15P31A504-165):** 편집 제작에서 운영자는 계획 일부 칸이 아니라 **작품 명세의 막히지 않은 모든 칸**을 고칠 수 있다. 지금 구현(S15P31A504-161 · 162)은 기존 요청 형식의 7칸(제목 · 표현 방식 · 주인공 · 드러내는 방식 · 분위기 · 색 · 반응 세기)만 고치며, S15P31A504-168에서 명세 전체 편집으로 바꾼다. 7칸으로 줄이지 않는 이유는 원문에서 뽑은 값까지 AI가 잘못 읽을 수 있어 운영자가 어느 칸이든 바로잡아야 하고, 칸마다 출처 · 원문 구절이 이미 명세에 함께 있어 화면에서 그대로 보여 줄 수 있기 때문이다.

편집 제작에서 운영자가 할 수 있는 일은 다음과 같다.

- 막히지 않은 모든 칸의 값을 바꾼다. 원문에서 뽑은 값(`extracted`)도 바꿀 수 있어, AI가 원문을 잘못 해석한 경우 바로잡을 수 있다.
- 선택 칸을 `"none"`으로 일부러 비운다. 필수 칸은 비울 수 없다(3.3).
- 막힌 칸(`null`)은 바꿀 수 없다.
- 편집 화면은 칸마다 출처(`origin`)와 원문 구절을 함께 보여 주고, 확신이 낮은 칸은 후보(`candidates`)를 함께 보여 준다(6.3).

원문에서 확인하지 못한 값은 ‘추출하지 못함’으로 남긴다. Head는 선택 가능한 창작 항목을 결정하되 **사용자가 말한 값과 AI가 기획한 값을 구분**한다. 원문이 값 목록에 없는 표현을 요구하면, **확신이 높을 때만** 같은 칸의 가까운 값으로 바꾸고 바꾼 사실을 기록한다. 확신이 낮으면 억지로 바꾸지 않고 원문 구절을 남기며, 필수 칸은 Head가, 선택 칸은 템플릿 기본값으로 채운다. 편집 제작에서는 운영자가 그 값을 후보 중에서 다시 고를 수 있다(6.2). 다만 **막힌 칸 요구·계열 불일치·제약 위반은 바꾸지 않고 해당 작업을 보류한다**(보류 대상은 6.2). 그 상태가 현재 작품의 재생을 중단시키지는 않는다.

작업이 시작된 뒤 결과를 바꾸고 싶으면 실행 중인 명세를 고치지 않고 예외 제어의 **수정본 생성**으로 새 명세 리비전과 새 작업을 만든다.

**계열은 Head가 바꾸지 않는다.** 원문이 선택한 계열과 맞지 않아 보이는 경우에도 임의 변경하지 않고 해당 작업을 보류한다. 예를 들어 흐름 계열을 선택했는데 원문이 특정 캐릭터의 등장을 요구하면 보류 대상이다.

값의 우선순위는 `운영자가 정한 값(편집 제작의 편집, 수정본 요청)·고정 조건 → 원문에서 확인한 요구 → Head의 선택 → 템플릿 기본값`으로 제안한다. 하드웨어·지원 기능·예산 제약은 모든 단계에서 검증한다. 우선순위를 프롬프트에만 적지 않고 서버에서 적용한다. 실행이 시작된 명세는 고정하며, 이후 수정은 새 명세 리비전과 새 작업으로 기록한다.

**계열 변경은 수정이 아니라 새 작품이다.** 계열이 바뀌면 명세 항목과 작업 그래프가 전부 달라지므로 같은 작품의 새 리비전으로 처리하지 않고 새 작품 요청으로 만든다.

### 5.1 입력 처리 단계

LLM은 원문 해석(③)과 빈 필수 칸 고르기(⑥) 두 가지에만 사용하며, **두 일을 한 번의 호출로 처리한다.** LLM이 원문과 모든 칸을 함께 보고 고르므로 값끼리 어울리고, 응답이 느린 로컬 LLM에서도 호출이 한 번으로 끝난다. 원문에서 뽑은 값과 Head가 고른 값은 칸마다 원문 구절이 있는지로 서버가 나눈다. 검증과 실행 값 변환은 코드가 수행한다.

| 단계 | 처리 | 수행 |
|---|---|---|
| ① 원문 저장 | 사용자가 쓴 문장을 그대로 저장한다. LLM 호출 전에 기록해 재해석·추적의 기준으로 삼는다 | 서버 |
| ② 계열 결정 | 요청에 포함된 계열(사용자 선택) 또는 자동 운영 정책의 계열을 기록한다 | 사용자·정책 |
| ③ 원문 해석 | 원문을 선택한 계열의 카탈로그 코드로 변환한다. 정규화와 코드 변환을 한 번의 호출로 처리하고, 카탈로그 목록을 입력에 포함한다. 목록 칸마다 원문 구절(`source_text`)·코드·확신도(`confidence`)를 함께 낸다. 칸별 구절 나누기와 코드 매칭을 같은 호출에서 함께 출력하므로 어느 쪽에서 틀렸는지 구분할 수 있다. 확신이 낮은 칸은 원문 구절을 코드로 바꾸지 않고 구절과 후보 코드를 남긴다(6.2). 같은 호출에서 ⑥의 빈 필수 칸 값도 함께 낸다. 서버는 원문 구절이 실제 원문에 있는지 확인하고, 구절이 있고 확신이 높은 값만 원문에서 뽑은 값(`extracted`)으로 기록한다 | LLM, 계열별 JSON Schema 구조화 출력 |
| ④ 지원 규격 검사 | 허용 코드·값 범위를 확인한다. ③이 바꾼 값도 다시 검사하며, 6.2의 보류 대상은 미지원으로 기록한다. 매질·반응 조합 문제는 19절 결정 전까지 보류하지 않고 기록만 한다 | 서버 |
| ⑤ 명세 리비전 저장 | 항목별 값과 출처(`origin`)·근거를 불변 리비전으로 저장한다 | 서버 |
| ⑥ 빈 항목 채우기 | 비어 있는 항목만 채운다. 두 모드 모두 필수 칸은 Head가 고르고(`head_selected`) 선택 칸은 템플릿 기본값(`template_default`)을 쓴다. 필수 칸 값은 ③과 같은 LLM 호출에서 함께 받는다(원문 구절이 없거나 확신이 낮은 칸의 값). 그 답에도 빈 필수 칸이 남으면 틀린 답으로 보고 다시 묻는다. 화면 깊이는 예외로 Head가 고르지 않고 `2.5d`를 쓴다(6.1 화면 깊이). 기본값이 없는 선택 칸은 비워 두고 `unextracted`로 기록한다. 원문에서 확인한 값은 바꾸지 않는다. 결과는 ④ 검사를 다시 거쳐 새 리비전으로 저장한다. 자동 제작은 ⑧로 넘어간다 | LLM(③과 같은 호출)·서버 |
| ⑦ 운영자 편집 (편집 제작만) | ⑥까지 채운 명세 전체를 운영자에게 보여 준다. 운영자는 막히지 않은 모든 칸을 고치고, 선택 칸은 `"none"`으로 비울 수 있다(3.3). 고친 칸은 `origin: user_explicit`로 기록하며, 고치기 전 값은 ⑥의 리비전에 남는다. 목록 칸의 선택지는 카탈로그 값만 보여 준다(허용 조합 기준은 19절 결정 후 적용). 결과는 ④ 검사를 다시 거쳐 새 리비전으로 저장한다. 필수 칸의 `"none"`처럼 검사를 통과하지 못하면 운영자에게 사유를 보여 주고 다시 고치게 한다 | 운영자 |
| ⑧ 실행 값 변환 | 명세 코드를 카탈로그의 대응표로 실행기 계약 값(예: 흐름 계열의 점성·감쇠·반경)으로 바꾸고 기존 계약 검증을 거쳐 조립 작업으로 넘긴다. **LLM이 실행기 숫자를 직접 쓰지 않는다** | 코드 |

- LLM 응답이 없거나 형식이 틀리면 1회 재시도하고, 그래도 실패하면 규칙 기반 기획으로 대체한다. 대체 사실은 명세 리비전에 기록한다.
- 사용한 모델·프롬프트 버전을 기록한다. 같은 원문·계열·카탈로그 스냅샷 조합은 ③의 결과를 재사용할 수 있다.
- 6.2의 보류 대상은 작업을 보류하고 사유를 기록한다. 사람이 승인하는 단계가 없으므로, 보류된 작품은 운영자가 예외 제어로 수정본을 만들거나 취소한다.

## 6. 작품 명세와 추출 근거

아래는 중앙 제작 프로그램의 명세 설계다. **UE가 직접 읽는 `scene.json`과는 구분**한다. 조립 어댑터가 검증된 카탈로그를 기준으로 기존 UE 계약에 맞게 변환한다. 명세의 칸과 계열별 상태는 3.3에 있다. 이 절은 목록으로 고르는 칸의 값(카탈로그), 자연어를 그 값에 매칭하는 규칙, 추출 근거를 다룬다.

명세에는 3.3의 칸 외에 호환 기준(UE·실행기 빌드, 카탈로그·명세·자산 규격 버전), 제작 제약(출력 규격, 허용 자산, 예산·기한, 사용자 고정 조건), 표현 템플릿(선택한 계열 안에서 실행기가 지원하는 것만)을 함께 기록한다. 이 값들은 원문에서 뽑지 않고 운영 설정과 카탈로그에서 정한다.

사용자 입력에서 모든 칸을 필수로 요구하지 않는다. 작업 실행에 필요한 값은 **선택한 계열의 템플릿과 실행기 계약에서 역산한다.** 선택 칸이 비어 있다는 이유만으로 전체 진행을 막지 않는다.

배경 추출 시 등장 객체가 섞이지 않도록 한다. 배경 생성 입력에 메인 캐릭터가 포함되면 배경 자산에도 같은 객체가 그려져 조립 결과에 중복으로 나타날 수 있다. 추출 규칙과 검수 항목 양쪽에서 확인한다.

### 6.1 값 목록 (카탈로그)

값마다 코드, 이름, **자연어 표현**(사람이 쓸 법한 비슷한 말)을 둔다. 자연어 표현이 매칭의 근거이며, 아래는 시작용 목록으로 계속 늘린다. 목록에 행을 추가하는 것만으로 TD·UE 기능이 구현되지는 않는다. "지금 되는 표현 방식"은 현재 프로토타입 [families.py](../../packages/contracts/src/contracts/families.py) 기준이며, 없거나 예정인 값은 실행기 구현 전까지 게시 대상에서 미검증으로 구분한다. **반응 코드는 계열별 적용 범위를 함께 기록한다.** 특정 반응이 한쪽 계열에서만 성립하는 경우 다른 계열의 선택지에 노출하지 않는다.

**계열** `template_family`

|---|---|---|

| 코드 | 이름 | 자연어 표현 |

| `appear` | 등장 | 사람이 오면, 나타나면, 앞에 서면, 있는 동안 |

| 코드 | 이름 | 뜻 |
|---|---|---|
| `once` | 한 번 일어남 | 입력이 들어온 순간 한 번 반응한다 |
| `while` | 입력하는 동안 계속 | 입력이 이어지는 동안 반응도 이어진다 |
| `accumulate` | 쌓임 | 입력이 반복될수록 반응이 커지거나 쌓인다 |

**복귀** `interactions[].return`

| 코드 | 이름 | 자연어 표현 |
|---|---|---|
| `instant` | 바로 돌아감 | 곧바로, 다시 들어감, 사라짐 |
| `fade` | 서서히 돌아감 | 잔상, 천천히 사라짐, 여운 |
| `stay` | 남아 있음 | 흔적이 남음, 쌓임 |

**드러내는 방식** `content.reveal` — 간접 표현(형상·흔적)을 기본 방향으로 두되 직접 그리는 작품도 만든다. 자세한 설명은 [작품 구조](../간접표현_작품구조.md)에 있다.

| 코드 | 이름 | 화면 | 자연어 표현 |
|---|---|---|---|
| `direct` | 직접 (신규) | 메인 캐릭터를 이미지로 직접 그림 | 뛰쳐나오는 호랑이, 서 있는 사슴 |
| `formation` | 형상 | 작은 것들이 모여 메인 캐릭터 모양이 됨 | ~로 만들어진, ~가 모여서 ~이 됨 |
| `trace` | 흔적 | 메인 캐릭터는 안 보이고 지나간 자국만 남음 | 발자취, 지나간 자리, 흔적만 |
| `field` | 없음 | 메인 캐릭터 없이 장(field)만. 현재 코드의 `Reveal.none` (3.3) | (메인 캐릭터가 없을 때) |

**매질** `content.medium` — 매질을 고르면 쓸 표현 방식이 사실상 정해진다.

| 코드 | 이름 | 자연어 표현 | 연결되는 표현 방식 |
|---|---|---|---|
| `particle` | 입자 | 물방울, 빗방울, 모래, 반딧불, 먼지 | 입자 |
| `swarm` | 무리 | 물고기 떼, 새 떼, 나비 떼 | 군집 |
| `fluid` | 유체 | 연기, 잉크, 물감 번짐, 안개 | 유체 |
| `surface` | 표면 | 수면, 천, 모래밭, 막 | 표면 변형 |
| `stroke` | 선 | 붓선, 빛줄기, 실, 궤적 | 그리기·혼합 |
| `light` | 빛의 장 | 오로라, 빛 번짐, 광채 | 없음 |

**스타일** `content.style` — 장면 계열의 배경·캐릭터 이미지 생성용. 실제로 쓸 이미지 생성 공급자가 잘하는 화풍에 따라 바뀔 수 있다.

| 코드 | 이름 | 자연어 표현 |
|---|---|---|
| `realistic` | 실사 | 사실적인, 사진 같은 |
| `illustration` | 일러스트 | 동화풍, 그림책 |
| `watercolor` | 수채화 | 번지는, 맑은 물감 |
| `ink` | 수묵화 | 동양화, 먹 |
| `pixel` | 픽셀 | 도트, 레트로 게임 |
| `3d` | 3D 렌더 | 입체적인, 게임 그래픽 |
| `minimal` | 미니멀 | 단순한 도형, 선만 |

**화면 깊이** `content.dimension` — 장면 계열에서 배경과 캐릭터를 평면으로 둘지, 앞뒤 층을 나눠 깊이감을 줄지 정한다. 흐름 계열에서는 막힌 칸이다. 초기 UE 연동은 고정 카메라의 2.5D를 기준으로 한다(11절). 그래서 원문에서 뽑은 값(`extracted`)만 그대로 쓰고, 원문 근거가 없으면 Head가 고르지 않고 `2.5d`로 정한다. 메인 캐릭터가 있는 장면도 배경과 캐릭터를 앞뒤 층으로 나누는 2.5D가 기본이며, 원문이 "그림책처럼" 같은 2D 표현을 쓸 때만 `2d`가 된다.

| 코드 | 이름 | 자연어 표현 |
|---|---|---|
| `2d` | 2D | 평면, 납작한, 그림책처럼, 2D |
| `2.5d` | 2.5D | 입체감, 깊이감, 앞뒤 층, 원근, 2.5D |

**영향 범위** `content.influence_range`: `local`(국소) / `wide`(광역)

**작품 전체 시간 구조** `idle.timeline`: `loop`(계속 반복, 기본) / `stages`(단계별로 바뀜) / `accumulate`(반응이 쌓이면 바뀜). 현재 프로토타입의 `Timeline` 값과 같다.

### 6.2 매칭 규칙

칸의 값을 **누가 읽는지**에 따라 처리가 다르다.

| 칸 종류 | 칸 | 읽는 쪽 | 처리 |
|---|---|---|---|
| 자유 텍스트 칸 | `theme`·`mood`·`composition`·`main_character`·`background`·`material`·`lighting`·`idle.description` | 이미지 생성 공급자의 프롬프트 | 매칭하지 않고 원문 구절을 그대로 쓴다 |
| 목록 칸 | `input`·`reaction`·`reaction_mode`·`return`·`medium`·`reveal`·`idle.motion`·`style` 등 | 실행기(UE·TD)와 지원 규격 검사 | 반드시 목록 코드로 바꾼다. 실행기는 이미 만들어진 동작만 실행하고, 코드여야 제작 전에 허용 범위·조합을 검사할 수 있다 |

목록 칸에서 원문 표현이 목록에 없을 때 AI가 채우는 방법은 두 모드가 같다. 편집 제작은 그 결과를 운영자가 편집 단계(5.1 ⑦)에서 고칠 수 있다는 점만 다르다.

| 경우 | 예 | AI가 채우는 방법 (두 모드 공통) | 편집 제작의 편집 화면 |
|---|---|---|---|
| 목록에 있음 | "사람을 향해 헤엄쳐 와" → `follow` | 그 값으로 채운다 | 채운 값과 원문 구절을 보여 준다 |
| 목록에 없지만 확신이 높음 | "일렁이며 퍼진다" → `ripple` | 가까운 값으로 바꾸고 `was_mapped`·`mapping_reason`에 원문과 이유를 남긴다 | 바꾼 사실과 원문을 함께 보여 준다 |
| 목록에 없고 확신이 낮음 | "포효하며" → ? | **억지로 바꾸지 않되, 필수 칸이어도 멈추지 않는다.** 원문 구절을 남기고, 필수 칸이면 Head가 다른 칸과 어울리는 값을 고르고(`head_selected`), 선택 칸이면 템플릿 기본값을 쓴다 | ‘확신 낮음’과 원문 구절을 표시하고, 가까운 후보를 앞에 둔 목록을 보여 준다 |
| 보류 대상 | 흐름 계열의 "호랑이 등장" | 바꾸지 않고 보류한다: 그 계열에서 막힌 칸 요구, 계열과 원문의 불일치, 하드웨어·예산 제약 위반 | 같음. 편집 화면으로 넘어가지 않는다 |

보류 대상은 위 세 가지로 한정한다. 셋 다 계열의 칸 상태(3.3)와 운영 제약처럼 **코드가 판단할 수 있는 기준**이다. 매칭이 안 된다는 이유만으로는 멈추지 않는다는 1.2의 원칙에 따라, 맞는 값이 없는 표현은 보류하지 않고 위의 ‘확신이 낮음’으로 처리한다. 매질과 반응이 서로 다른 표현 방식을 가리키는 조합의 처리는 19절에서 정하며, 정해지기 전까지 보류 대상에 넣지 않는다.

**못 맞춘 원문 구절은 버리지 않는다.** 목록 칸에 들어가지 못한 구절은 명세의 `unmatched_phrases`에 남기고 세 곳에서 쓴다.

- **생성 단계:** 장면 계열이면 배경·캐릭터 생성 프롬프트에 분위기로 반영할 수 있다. 예를 들어 반응 칸에 못 들어간 "포효하며"는 캐릭터 프롬프트의 "포효하는 호랑이"로 쓸 수 있다. 실행기 값에는 쓰지 않는다.
- **운영 화면:** 원문의 어느 부분이 동작에 반영되지 않았는지 보여 준다.
- **카탈로그 확장:** 자주 나오는 미매칭 표현을 모아 새 값(예: `roar`)의 추가 근거로 쓴다.

예를 들어 "점프하면 호랑이가 포효하며 땅이 울린다"에서 "땅이 울린다"는 `ripple`의 자연어 표현(땅이 울림)에 있어 그대로 채운다. "포효하며"는 맞는 반응이 없으므로 `ripple`에 억지로 합치지 않고 `unmatched_phrases`에 남겨 캐릭터 생성 프롬프트와 미매칭 기록에 쓴다.

Head에는 선택한 계열에서 막히지 않은 칸 목록과 각 칸의 값 표(코드·이름·자연어 표현)만 넘기고, 결과는 목록 코드로만 받는다. 서버는 받은 값이 카탈로그에 있는지, 계열에서 허용되는지 다시 검사한다. 값의 우선순위는 5절을 따른다.

### 6.3 추출 근거

각 명세 리비전은 다음 근거를 함께 저장한다.

| 필드 | 내용 |
|---|---|
| `field_path`, `value` | 어떤 명세 항목의 어떤 값인지 |
| `origin` | `user_explicit`, `extracted`, `head_selected`, `template_default`, `unextracted`(원문에서 값을 정하지 못함) 등 출처 |
| `source_text` | 원문에서 이 칸에 해당하는 구절. 매칭하지 못한 칸도 구절을 남긴다 |
| `confidence` | 목록 칸 매칭의 확신도(`high`·`low`). 기준값은 19절 미정 항목 |
| `candidates` | 확신이 낮은 칸의 후보 코드. 편집 제작 모드의 편집 화면에서 선택지 순서에 쓴다 |
| `was_mapped`, `mapping_reason` | 지원 코드로 변환한 사실과 이유 |
| `user_edited` | 수정본 요청에서 운영자가 명시적으로 바꾼 값인지. 편집 제작 모드의 편집 단계(5.1 ⑦)에서 고친 값은 `origin: user_explicit`이며 `user_edited`가 아니다 |
| `model_ref`, `prompt_version` | 사용 모델·프롬프트 버전. 선택 전에는 미정 |
| `validation_result` | 지원 규격 검사와 필요한 보류 사유 |
| `unmatched_phrases` | 목록 칸에 들어가지 못한 원문 구절과 해당 칸. 명세 리비전에 함께 저장하고 생성 단계·운영 화면에 넘긴다 |

`origin` 값의 뜻은 다음과 같다. 위의 네 값은 위에서 아래 순서가 5절의 값 우선순위와 같다.

| 코드 | 뜻 |
|---|---|
| `user_explicit` | 운영자가 직접 정한 값. 편집 제작 모드에서 고치거나 `"none"`으로 비운 값, 수정본 요청에서 바꾼 값(이때는 `user_edited`도 표시) |
| `extracted` | 원문에서 뽑은 값 |
| `head_selected` | 원문에 없거나 확신이 낮아 Head가 고른 값 |
| `template_default` | 비어 있어 템플릿 기본값을 쓴 값 |
| `unextracted` | 원문에서 값을 정하지 못해 비어 있는 칸. 기본값이 없는 선택 칸 등. 값이 없으므로 우선순위에 들지 않는다 |

계열 값의 `origin`은 `user_explicit` 또는 운영 정책 출처로 기록하며 `head_selected`를 사용하지 않는다.

추출 근거는 감사 기록에만 두지 않는다. 운영 화면은 칸별 값 옆에 `source_text`를 보여 주고, 생성 단계는 `unmatched_phrases`와 자유 텍스트 칸의 구절을 프롬프트에 쓴다.

### 6.4 명세 예시

아래는 설명용 명세 예시다. 꺾쇠 값은 실제 카탈로그에서 채울 참조이며, 현재 UE에 바로 전달할 수 있는 파일이 아니다. 지면을 줄이려고 비어 있는 선택 칸과 출처 기록 일부는 생략했다. `theme`·`mood`는 필수 칸이라 원문에 없으면 Head가 채운다. 이 스키마의 코드는 `packages/contracts`의 `spec.py`에 있다.

장면 계열 · 형상 예시 — 장면 계열에서 흐름 쪽 칸(`medium`)을 연 경우:

```json
{
  "spec_schema_version": "proposal-2",
  "mode": "auto",
  "template_family": "scene_family",
  "raw_prompt": "수많은 물방울로 만들어진 고래가 헤엄치는 장면. 헤엄칠 때마다 꼬리나 지느러미에서 물방울이 잔상처럼 남고 고래는 사람을 향해 헤엄쳐 와",
  "catalog_snapshot_id": "<검증된 카탈로그 참조>",
  "template_ref": "<scene_family에 속한 지원 템플릿>",
  "content": {
    "theme": "다가오는 바다",
    "mood": "고요하고 신비로움",
    "main_character": "물방울로 이뤄진 고래 한 마리",
    "reveal": "formation",
    "background": "<Head가 채움: 필수>",
    "dimension": "2.5d",
    "medium": "particle"
  },
  "idle": {"motion": null, "description": "고래가 천천히 헤엄침", "timeline": "loop"},
  "interactions": [
    {"input": "appear", "reaction": "follow", "reaction_mode": "while", "return": "fade", "duration_sec": null}
  ],
  "display_policy": "until_next_applied",
  "provenance": [
    {"field_path": "template_family", "origin": "user_explicit", "source_text": null},
    {"field_path": "content.theme", "origin": "head_selected", "source_text": null},
    {"field_path": "content.mood", "origin": "head_selected", "source_text": null},
    {"field_path": "content.medium", "origin": "extracted", "source_text": "수많은 물방울로 만들어진"},
    {"field_path": "interactions[0].reaction", "origin": "extracted", "source_text": "사람을 향해 헤엄쳐 와"},
    {"field_path": "interactions[0].return", "origin": "extracted", "source_text": "물방울이 잔상처럼 남고"},
    {"field_path": "idle.motion", "origin": "unextracted", "source_text": "고래가 헤엄치는", "confidence": "low",
     "candidates": ["follow", "swirl"]}
  ],
  "unmatched_phrases": [{"field_path": "idle.motion", "text": "고래가 헤엄치는"}]
}
```

`idle.motion`은 장면 계열에서 선택 칸이고 "헤엄침"에 맞는 값이 목록에 없어 확신이 낮으므로 억지로 바꾸지 않았다. 구절은 `unmatched_phrases`에 남고, 이 템플릿에는 평상시 움직임 기본값이 없어 비워 둔다(19절 미정 항목).

## 7. 작업 큐·의존성·실행 동시성

| 논리 큐 | 담당 작업 | 실행 위치·조건 | 계열 |
|---|---|---|---|
| 기획 큐 | 원문 해석, Head 기획, 명세·지원 범위 검사 | 중앙 Worker | 공통 |
| 배경 생성 큐 | 배경 이미지·영상 생성 접수·결과 회수 | 외부 공급자 어댑터 | 장면 |
| 에셋 생성 큐 | 준비된 배경을 참조한 시각 에셋 생성 | 외부 공급자 어댑터 | 장면 |
| 전처리 큐 | 규격 변환, 마스크·반응 영역·필요한 흐름 데이터 | 해당 도구를 갖춘 Worker | 주로 장면 |
| **공통 UE 조립 큐** | 데이터 조립·프리뷰·UE 기술 검증 | 제작 노드 N대가 공유; 노드별·계열별 전용 큐로 고정하지 않음 | 공통 |
| 검수 큐 | 파일·에셋·조합·상호작용·복귀·성능 평가 | 검수 서비스; 추가 UE 실행은 제작 노드의 같은 실행 제한 적용 | 공통(항목은 계열별) |
| 게시 큐 | 승인 버전 선택, 전달·교체·실제 적용 추적 | 중앙 게시자; 시연 대상별 한 요청씩 처리 | 공통 |

흐름 계열 작업 그래프에는 배경·에셋 생성 큐 작업이 생성되지 않는다. 전처리는 템플릿이 별도 입력 데이터를 요구할 때만 사용한다. **조립 큐는 계열과 무관하게 공유한다.** 계열별 전용 큐를 두면 한쪽 계열의 작업이 몰릴 때 가용 노드를 활용하지 못한다.

큐에 쌓인 작업 수와 실행 중인 작업 수를 별도 지표로 관리한다. 제작 노드당 조립은 한 번에 1개다. 기획·생성·전처리의 동시성, 큐 대기 한도, 공급자 호출 한도, 재시도 횟수와 시간 제한은 실측·예산·계약 후 정할 설정값으로 두며 이 문서에서 임의 수치를 넣지 않는다.

RabbitMQ는 전달, PostgreSQL은 작업 상태의 기준, Celery는 중앙 비동기 작업 실행을 맡는다. Windows 제작·시연 노드는 Celery Worker로 직접 실행하지 않는다. Celery 공식 문서가 Windows를 지원 대상에서 제외하므로 Python Agent가 FastAPI를 통해 작업을 받는 기존 선택을 유지한다. [Celery Windows 안내](https://docs.celeryq.dev/en/stable/faq.html#does-celery-support-windows)

**구현 제안 — 중앙 조립 디스패처:** RabbitMQ의 조립 메시지를 중앙에서 수신해 PostgreSQL의 배정 가능 상태에 반영한 뒤 처리 확인한다. Agent는 FastAPI에서 이 공통 작업 집합의 작업 하나를 임대한다. 메시지 수신은 조립 성공이 아니며, 배정 후 완료까지는 DB의 작업·시도 기록으로 추적한다. 브로커와 DB를 각각 독립적인 최종 상태로 취급하지 않는다.

DB 변경과 메시지 발행 사이의 누락을 막기 위해 같은 트랜잭션에 발행 예정 이벤트를 기록하는 outbox와 재전송·재대조를 제안한다. 중복 메시지는 작업 ID와 멱등 키로 처리한다. 이 구현 패턴은 신규 제품을 추가하는 선택이 아니며, 실제 ACK·재전달·장애 복구 동작을 통합 시험해야 한다.

작품별 의존성은 작업 간 관계로 기록한다. 상위 결과가 변경되면 그 결과에 의존하는 조립·검수 산출물을 다시 평가한다. 재사용 가능한 상위 결과가 있으면 보존하고 실패 단계부터 재시도한다. 실패한 모든 작업을 처음부터 유료 생성으로 되돌리지 않는다.

## 8. 작업 임대·heartbeat·늦은 결과 처리

모든 단계에서 `artwork_id`, `artwork_version_id`, `job_id`, `attempt_id`, `node_id`를 연결한다. 중앙 Worker처럼 물리 제작 노드가 아닌 실행 주체에는 별도 `worker_id`를 사용한다. Agent 재시작 구분을 위한 세션 ID와 작업 소유권 토큰도 기록한다.

1. Agent가 자신과 실행 환경·가용 상태를 보고한다. 중앙은 호환 카탈로그·런타임과 선행 작업 완료를 확인한다.
2. 짧은 DB 트랜잭션에서 작업을 선택하고 새 시도·임대 만료 시각·증가한 소유권 토큰을 기록한다. 노드에 활성 UE 작업이 있으면 추가 배정하지 않는다.
3. Agent는 heartbeat로 작업 임대를 갱신한다. 노드 생존 신호와 개별 작업의 임대 갱신은 구분한다.
4. 결과는 시도별 임시 저장 경로에 업로드한다. 완료 보고 시 중앙이 작업·시도·소유권 토큰·임대·노드 세션·입력 버전을 함께 대조한다.
5. 임대가 만료되거나 새 시도로 교체된 작업의 늦은 결과는 성공 상태나 승인 번들에 반영하지 않는다. 임시 결과는 격리 후 정리 정책에 따른다.
6. 제작 Agent는 임대를 유지할 수 없으면 새 작업을 시작하지 않고 진행 작업의 중단·정리를 수행한다. 재연결 뒤 상태를 대조하고, 이전 UE 종료를 확인한 뒤 다음 UE 작업을 시작한다.

DB 행 잠금은 배정·갱신 시점에만 짧게 사용한다. 이미지 생성이나 UE 실행이 끝날 때까지 트랜잭션을 열어 두지 않는다. DB 제한과 함께 Agent의 프로세스 관리·장비 내 단일 실행 잠금을 적용한다. 토큰은 오래된 결과 반영을 막는 수단이며, 이미 외부 공급자에 접수된 유료 호출까지 되돌리는 수단은 아니다. 공급자 작업 ID와 지원되는 멱등 키를 보존해 재접수 전에 기존 결과를 조회한다.

## 9. 제작 노드 N대의 공통 내부 구성

| 구성요소 | 모든 제작 노드가 동일하게 수행하는 기능 |
|---|---|
| Node Agent | 작업 수신·임대·heartbeat, 작업 폴더와 UE 프로세스 관리 |
| 자산 준비 | 다운로드·해시·규격·호환성 검사, 로컬 캐시 재사용 |
| UE Assembly Worker | 명세를 기존 scene 계약으로 변환하고 계열에 따라 자산 조립 또는 파라미터 구성 |
| 인터랙션 연결 | 공통 카탈로그의 입력·조건·반응·복귀 규칙 연결 |
| 기술 검증 | 모의 손 입력, 프리뷰, 참조·디코딩·복귀·성능 측정 |
| 산출물 전달 | 실행 번들·미리보기·검증 증거·로그 업로드, 중앙 결과 보고 |

조립 어댑터는 계열에 따라 변환 경로가 다르다. 장면 계열은 배경·에셋·재질·효과를 scene 계약에 배치하고, 흐름 계열은 템플릿이 요구하는 파라미터를 같은 계약의 해당 필드로 변환한다. **두 경로 모두 기존 실행기 계약을 사용하며 계열별로 별도 실행기를 두지 않는다.**

노드 1의 작품 A와 노드 2의 작품 B는 작업 예시일 뿐 역할 분담이 아니다. 계열에 따라 노드를 나누지도 않는다. 모든 제작 노드는 두 계열을 모두 처리한다. 노드 증설은 같은 코드·엔진·플러그인·카탈로그·실행 규격을 갖추고 등록·호환 검사를 통과하는 방식으로 한다. N은 무제한 성능을 뜻하지 않으며 공급자·저장소·네트워크·중앙 서비스의 처리량도 함께 고려한다.

에디터가 필요한 콘텐츠는 제작 노드에서 처리한다. 에디터 작업 종료·프로세스 종료 확인 후 별도 검증 실행본을 실행한다. 자동 검수 재실행이 UE를 요구하는 경우에도 동일 노드에서 기존 UE와 겹치지 않도록 배정한다. 제작 중인 파일을 승인 번들 경로에 직접 덮어쓰지 않는다.

## 10. 자동 검수와 재작업

| 검사 | 확인할 내용 | 계열 | 실패 시 기본 반환 경로 |
|---|---|---|---|
| 파일·규격·호환성 | 파일 존재·해시·디코딩·크기·참조 경로·실행기/카탈로그 버전 | 공통 | 다운로드 재시도, 전처리 또는 재조립 |
| 개별 에셋 | 손상·알파·잘림·불필요한 배경·요구 역할 충족 | 장면 | 해당 에셋 재생성 또는 전처리 |
| 배경·에셋 조합 | 스타일·색감·재질·크기·배치·공간감의 일관성, 배경의 객체 중복 여부 | 장면 | 배경/에셋 재생성 또는 배치 재조립 |
| 파라미터 유효성 | 매질·운동 규칙·영속성 조합의 지원 여부, 밀도·범위의 허용 구간 | 흐름 | 파라미터 수정 후 재조립 |
| 거동 관찰 | 무입력 상태 거동, 입력 중 반응, 입력 종료 후 소멸·축적이 명세와 일치하는지 | 흐름 | 파라미터 수정·재조립; 공통 코드 결함은 별도 개발 이슈 |
| 인터랙션·복귀 | 입력 전·반응 중·입력 종료 후 동작, 지원 조합, 모의 입력 결과 | 공통 | 설정 수정·재조립; 공통 코드 결함은 별도 개발 이슈 |
| 성능 | 목표 장비의 프레임 시간·메모리·VRAM·미디어 준비·반복 교체 비용 | 공통 | 규격 축소·효과/배치 조정·재조립 |
| 장시간 안정성 | 지속 실행 시 메모리 증가·파티클 누적·프레임 저하 | 흐름 | 밀도·영속성 조정·재조립 |
| 게시 준비 | 번들 완결성, 모든 검사 결과, 호환 기준, 자산 이용 조건 | 공통 | 필요한 단계만 보완 후 재검수 |

**정의된 필수 자동 검수를 모두 통과하면 게시 승인으로 처리**한다. 매 작품의 운영자 승인 클릭은 기본 경로에 넣지 않는다. 자동화가 아직 구현되지 않은 검사 항목을 통과로 간주하지 않고 ‘미검증’으로 구분한다. 프로토타입의 대표 사례로 검사 기준을 정립한 뒤 자동 판정 범위를 넓힌다. **계열별 필수 검사 목록은 각각 정의하며, 한쪽 계열의 통과 기준을 다른 계열에 그대로 적용하지 않는다.**

흐름 계열은 생성 자산이 없어 파일·에셋 검사 비중이 작은 대신 거동과 장시간 안정성 검사가 중요하다. 고정 길이 클립이 아니라 다음 작품이 적용될 때까지 실행되므로, 짧은 프리뷰만으로 통과 판정하지 않는다. 관찰 시간과 판정 기준은 실측 후 정할 설정값으로 둔다.

검수 결과에는 검사 규칙 버전, 검사 대상 번들 해시, 증거·측정값, 실패 원인, 재작업 목적지를 남긴다. 재시도 예산이나 시간 제한을 넘으면 해당 작품을 보류하고 다음 가능한 작업을 처리하며 현재 전시는 유지한다. 공통 실행기 버그에 대해 자산만 반복 재생성하지 않는다.

## 11. 자산 저장소·버전 번들·로컬 캐시

PostgreSQL에는 자산 메타데이터와 참조를 저장하고, 이미지·영상·UE 콘텐츠 파일은 AssetStore를 통해 저장한다. **초기 AssetStore는 생성 PC 1대의 전용 디스크 데이터 폴더를 SMB 공유**한다. UE 제작 초기 2대와 시연 1대가 같은 공유 저장소를 사용하며 제작 노드 N대 확장 시에도 경로 계약을 유지한다. 별도 저장 PC·NAS·S3를 초기 구성에 추가하지 않는다. **생성 자산을 EC2 인스턴스 디스크에 적재하지 않는다.** 실제 폴더·접근 계정·권한·대역폭·용량·백업은 [저장소 배치](../../infra/STORAGE.md)에 따라 확인하며, 다른 저장 장비로의 전환은 필요성이 확인되면 별도 결정한다.

| 구분 | 관리 내용 |
|---|---|
| 공급자 원본 | 생성 요청·공급자 작업 ID·원본 파일·출처·이용 조건 |
| 가공 자산 | 변환·마스크·반응 영역·필요한 흐름/깊이 데이터, 원본과 처리 버전의 관계 |
| 재사용 라이브러리 | 검증된 공통 자산·템플릿·자산 메타데이터·사용 범위 |
| 후보 번들 | 조립 시도별 작업 공간, 미리보기, 검수 전 결과 |
| 승인 번들 | 버전별 불변 파일·해시 목록·호환 정보·검수 근거 |
| 노드별 로컬 캐시 | 중앙 자산 ID/해시에 대응하는 장비별 파일 위치 |

흐름 계열은 공급자 원본·가공 자산이 거의 발생하지 않는다. 승인 번들에는 설정과 미리보기가 중심이 되며 번들 크기가 작다. 저장 정책의 실측에는 두 계열의 비율을 반영한다.

자산의 기준 주소는 `asset_id / storage_key / content_hash`다. 특정 PC의 절대 경로를 다른 PC에 전달하지 않는다. 원본·가공본·번들·작품 참조를 분리해 같은 파일의 재사용과 생성 이력을 추적한다. `AssetStore`는 저장·조회·다운로드·무결성·원자적 공개를 공통 인터페이스로 제공한다. 실제 원격 저장 구현에는 인증·전송 실패·재개·완결성 확인이 추가로 필요하다.

썸네일을 별도 관리해 목록 조회에서 원본 전체를 내려받지 않는다. 저장 정책에는 파일 크기, 보존 버전, 캐시 복제, 공급자 원본, 영상·프레임 시퀀스를 포함한 실측치를 사용한다. 보존 기간과 삭제 기준은 미정이며 임의로 90일을 확정하지 않는다.

현재 활성·준비 중·마지막 정상 버전과 실행 중 작업이 참조하는 파일은 정리에서 보호한다. 작품 목록에서 항목을 숨기는 것과 실제 공유 파일 삭제는 별도 동작으로 한다. 미참조·미보호 파일에 한해 정책에 따라 회수하고 삭제 이력을 남긴다.

런타임 이미지·영상·설정 번들과 사전 쿠킹 UE 콘텐츠는 구분한다. 일반 자산은 기존 실행기가 지원하는 계약으로 준비하고, 스켈레탈 등 쿠킹이 필요한 자산은 제작 측에서 처리한다. 공통 골격·동작 틀의 재사용과 과거 완성 작품의 외형 재사용은 별도 정책이다. 자동 제작이 과거 작품의 반복 사용으로만 구성되지 않도록 새 자산 요구를 명세에 남긴다.

초기 UE 연동은 **고정 카메라의 2.5D와 검증된 손 반응**을 기준으로 한다. 검토한 런타임의 일반 이미지 경로는 PNG/JPG 최대 4096×4096, 영상은 같은 버전의 대체 정지 이미지를 갖춘 MP4를 요구한다. 정적 OBJ도 지원되는 제한 형식과 좌표·단위를 따라야 한다. 쿠킹된 스켈레탈 팩은 같은 엔진·프로젝트·대상 플랫폼 및 RigProfile 계약을 확인하는 후속 확장 경로로 두며, 실제 마운트·수명·메모리 제한을 반복 운용에서 검증한다. 흐름 계열이 요구하는 자산·파라미터 계약은 3.4의 확인 항목에 따른다. [기존 자산 계약](https://github.com/lanael-studio/interactive-runtime/blob/613e6a86ab04d3f87435557ef9186846fce88a8b/Docs/references/implementation/LiveContentArchitecture.ko.md#L104)

## 12. 시연 노드와 실제 적용 확인

시연 노드는 신규 코드 빌드·에디터 조립·쿠킹을 수행하지 않는다. Show Agent와 UE Runtime 한 개가 아래 작업을 수행한다. 다음 작품 준비는 같은 UE 프로세스 안에서 이루어지며 두 번째 UE를 실행하는 방식으로 대체하지 않는다. **계열이 달라도 같은 Runtime과 같은 교체 절차를 사용한다.**

| 단계 | 중앙 게시자·Show Agent | UE Runtime |
|---|---|---|
| 전달 | 승인 버전 선택, 다운로드·무결성·호환성 검사, 로컬 후보 완성 | 현재 작품 A 실행 |
| 준비 요청 | 명확한 대상 버전·명령 ID로 요청 | A를 유지하면서 B 자산·설정을 비동기 준비 |
| Ready | 실제 준비 상태를 중앙에 보고 | B가 활성화 가능한 준비 단계에 도달 |
| 교체 | 목표 제어 계약에 따라 교체 요청 | B 활성화, 이전 장면 정리 |
| Applied | 실행 세션·요청·실제 활성 버전을 대조해 적용 기록 | 실제 활성 장면·버전 결과 보고 |

흐름 계열에서 교체는 진행 중이던 입자·궤적 상태의 정리를 포함한다. 이전 작품의 누적 상태가 다음 작품으로 이어지지 않도록 하는 처리는 실행기 계약에서 확인할 항목이다.

**목표 제어 계약과 현재 저장소 경로를 구분한다.** 검토한 기존 런타임은 `AArtworkSceneHost`가 `scene.json`·`release.json`을 읽고 비동기 준비를 수행하며 기본 자동 Commit을 사용한다. UE 내부의 준비·Commit API와 중앙에서 호출할 원격 API는 같지 않다. 명시적인 `Prepare → Ready → Commit` 제어를 하려면 Show Agent와 UE 사이의 어댑터를 구현·검증해야 한다.

초기 연동 제안은 기존 파일 게시·자동 Commit 경로에서 적용 관측까지 연결하는 것이다. 이 경로에서는 짧은 Ready 상태를 관측하지 못하고 Applied를 먼저 읽을 수 있으므로, 관측하지 않은 Ready를 만들어 보고하지 않는다. 이 초기 연동을 중앙의 명시적 교체 제어까지 완성한 것으로 표시하지 않는다. 교체 시점 제어 방식의 최종 선택은 어댑터 설계 항목으로 남긴다.

기존 파일 계약에서는 완성된 `versions/<Version>/` 디렉터리와 그 안의 `scene.json`·자산을 준비한 뒤 포인터를 원자적으로 바꾼다. 중앙 게시자의 지시를 받는 Show Agent 한 곳만 현장 포인터를 작성하며, 하나의 시연 대상에 여러 게시자가 동시에 쓰지 않는다.

```json
{"SchemaVersion": 1, "Version": "artwork_b_v001"}
```

이 예시는 기존 `release.json` 형식이다. `JobId`, 공급자 ID, 자체 명세 필드, 계열 코드를 임의로 추가하지 않는다. 외부 DB에서 작업 ID와 버전·해시·게시 명령·계열을 연결한다. 자산은 완성된 로컬 버전 폴더에 두고, 일반 외부 이미지·영상·OBJ의 파일 필드에는 로더가 허용하는 파일명만 사용한다. 다운로드 URL·임의 절대 경로·생성 중 파일을 직접 넣지 않는다. 스켈레탈 팩의 참조 형식은 해당 팩 계약을 별도로 따른다.

적용 완료는 `Phase=Applied`, `Applied=true`, 요청 버전과 실제 활성 버전 및 예상 SceneId가 맞는 **이번 실행 세션의 새 결과**로 판단한다. `RuntimeSessionId`, `ProcessId`, `RequestId`를 함께 대조한다. Ready·파일 전달 완료·포인터 변경은 각각 Applied와 다른 상태다. 이 결과는 실행기의 기술적 활성화 증거이며 관람 화면의 품질·무중단 성능 검증과도 구분한다.

통신 복구 시 중앙이 마지막으로 보낸 버전을 바로 재명령하지 않는다. Show Agent가 현재 세션·실제 활성 버전·진행 요청을 읽어 중앙에 보고하고 대조한 뒤 다음 교체를 결정한다. 확인되지 않은 적용은 `확인 대기`로 표시하고 새 유료 생성으로 되돌리지 않는다. 이미 적용된 작품을 되돌리는 것은 취소가 아니라 보존된 정상 버전을 대상으로 하는 새 교체 요청이다.

## 13. 장애·취소·복구 정책

| 상황 | 제작·제어 처리 | 시연 동작 |
|---|---|---|
| 운영 앱 종료 | 중앙 작업·Agent 계속 실행; 재접속 시 상태 복원 | 현재 작품 계속 실행 |
| 외부 AI 지연·일시 오류 | 공급자 작업 조회, 제한된 재시도·대기. 흐름 계열 작업은 영향 없음 | 현재 작품 계속 실행 |
| 생성 요청 거절·미지원 요구 | 원인 기록, 허용 범위 내 수정·보류; 정책 우회 재요청 금지 | 현재 작품 유지 |
| 선택 계열과 원문 불일치 | 계열을 임의 변경하지 않고 보류. 변경이 필요하면 새 작품 요청 | 현재 작품 유지 |
| 제작 노드 이탈 | 임대 만료·시도 분리·재배정; 늦은 결과 반영 차단 | 영향 없이 현재 작품 유지 |
| 다음 작품 준비 실패 | 실패 단계만 보완·재시도; 손상 후보 게시 금지 | 현재 작품 유지 |
| 중앙 통신 단절 | 신규 배정·게시 확인 제한; 복구 후 상태 대조 | 로컬 현재 작품과 카메라 → TD → UE 입력 계속 |
| Ready/Applied 보고 지연 | 결과 확인 대기; 명령·세션·활성 버전 조회 | 실제 런타임 상태 유지 |
| 게시 전 취소 | 대기 작업 취소, 실행 중 작업 중단 요청, 늦은 결과 격리 | 현재 작품 유지 |
| 게시 후 취소 요청 | UE 요청 단계 확인; 취소 지원 계약에 따라 처리 | 이미 Applied라면 새 복구 요청으로 처리 |
| UE 또는 시연 PC 자체 장애 | 원인·재시작 기록, 정상 번들로 복구 | 재시작 동안 중단 가능; 무중단을 보장하지 않음 |

마지막 정상 작품은 로컬 파일과 메타데이터를 함께 보존한다. 초기 SQLite 도입 없이 파일·원자적 상태 기록으로 필요한 복구 정보를 유지할 수 있도록 설계한다. 이후 로컬 조회·초안·이벤트 보관 요구가 커지면 SQLite 추가를 검토한다. 중앙 PostgreSQL을 대체하거나 모든 작품 상태를 양방향 복제하는 계획은 아니다.

## 14. PostgreSQL 데이터 모델

작품 ID는 작품의 정체성, 명세 리비전은 기획 변경, 작품 버전은 실행 후보·번들 변경, 작업 ID는 단계 작업, 시도 ID는 재시도를 구분한다. 생성 완료·조립 완료·검수 통과·게시·실제 적용을 하나의 `done` 상태에 합치지 않는다.

| 테이블·기록 제안 | 핵심 내용 |
|---|---|
| `projects`, `artworks` | 프로젝트·작품 소속, 원문, 작성 주체·접근 범위, 표현 템플릿 계열 |
| `spec_revisions` | 작품별 불변 명세 리비전, JSONB 명세(계열별 항목 포함), 지원 규격 검사 결과 |
| `slot_provenance` | 리비전·필드별 출처·원문·매핑·수정·모델·프롬프트 정보 |
| `catalog_snapshots`, `catalog_entries`, `interaction_pairs` | 버전별 지원 기능·표현·입력·반응·허용 조합과 **계열 구분**; 실제 UE/TD 규격과 대응 |
| `artwork_versions` | 명세 참조, 배포 버전 키, 번들 주소·해시, 실행기/카탈로그 해시, 예상 SceneId |
| `jobs`, `job_dependencies` | 단계·상태·입력 해시·선행 작업·멱등 키·재시도 정책 참조 |
| `job_attempts` | 시도·실행 주체·Agent 세션·소유권 토큰·임대·시각·오류·결과 |
| `nodes` | 제작/시연 역할, 호환 환경·가용 상태·최근 heartbeat·현재 Agent 세션 |
| `assets`, `asset_derivations`, `version_assets` | 원본·가공 관계, 저장 키·해시·크기·출처·이용 범위, 버전별 참조 |
| `quality_checks` | 후보·검사 규칙 버전·대상 해시·검사 결과·증거·재작업 사유·적용 계열 |
| `deployments` | 시연 대상, 승인 버전, 게시 명령 ID·순서, 전달·준비·교체·확인 상태 |
| `show_observations` | 실제 활성 버전·SceneId·RuntimeSessionId·ProcessId·RequestId·관측 시각 |
| `provider_requests`, `api_usage` | 공급자 작업 ID·중복 방지 키·조회 상태·입출력·실제 비용·통화·미확인 여부 |
| `job_events`, `outbox_events` | 진행 이력·재연결 후 조회 위치, DB 변경에 대응하는 발행 예정 이벤트 |

계열은 `artworks`에 컬럼으로 두고 `spec_revisions`의 JSONB에도 같은 값을 기록한다. 작품 단위로 계열이 고정되므로 리비전마다 바뀌지 않으며, 계열 변경 요청은 새 작품으로 처리한다. **계열별 파라미터는 별도 테이블을 만들지 않고 JSONB 안에 둔다.** 계열이 추가될 때 테이블이 늘지 않고 명세 불변성을 한 곳에서 관리할 수 있기 때문이며, 항목 검증은 계열별 JSON Schema로 서비스에서 수행한다.

인증 주체·권한과 작품 소속을 연결하되 로그인 방식·OAuth 공급자는 아직 확정하지 않는다. 배포용 앱에 공급자 비밀 키나 DB 접속 자격 증명을 넣지 않는다. API·Agent 인증과 비밀 관리의 구체 방식은 배포 설계에서 정한다.

다음 DDL은 **작업·버전·임대·계열 구조를 설명하는 PostgreSQL 설계 예시**다. 위 전체 테이블을 구현한 마이그레이션이 아니며 실제 PostgreSQL에서 실행·동시성 시험한 결과는 아니다. UUID는 애플리케이션에서 생성하는 예시로, 별도 UUID 확장을 전제하지 않는다.

```sql
CREATE TABLE artworks (
    artwork_id UUID PRIMARY KEY,
    title TEXT NOT NULL CHECK (length(btrim(title)) > 0),
    template_family TEXT NOT NULL
        CHECK (template_family IN ('scene_family','flow_family')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE spec_revisions (
    spec_id UUID PRIMARY KEY,
    artwork_id UUID NOT NULL REFERENCES artworks(artwork_id),
    revision INTEGER NOT NULL CHECK (revision > 0),
    raw_prompt TEXT NOT NULL CHECK (length(btrim(raw_prompt)) > 0),
    template_family TEXT NOT NULL
        CHECK (template_family IN ('scene_family','flow_family')),
    spec JSONB NOT NULL CHECK (jsonb_typeof(spec) = 'object'),
    provenance JSONB NOT NULL DEFAULT '[]'::jsonb
        CHECK (jsonb_typeof(provenance) = 'array'),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (artwork_id, revision),
    UNIQUE (artwork_id, spec_id)
);

-- 리비전의 계열이 작품의 계열과 어긋나지 않도록 강제한다.
-- 계열 변경은 수정이 아니라 새 작품 요청으로 처리한다.
ALTER TABLE spec_revisions
    ADD CONSTRAINT spec_family_matches_artwork
    FOREIGN KEY (artwork_id, template_family)
    REFERENCES artworks(artwork_id, template_family);

ALTER TABLE artworks
    ADD CONSTRAINT artworks_family_key
    UNIQUE (artwork_id, template_family);

CREATE TABLE catalog_entries (
    catalog_snapshot_id UUID NOT NULL,
    entry_code TEXT NOT NULL CHECK (length(btrim(entry_code)) > 0),
    entry_kind TEXT NOT NULL CHECK (entry_kind IN
        ('template','style','medium','reveal','dimension','influence_range','timeline',
         'interaction_input','interaction_response','reaction_mode','return')),
    -- interaction_response는 평상시 움직임(idle.motion)에도 쓴다
    -- natural_phrases는 매칭에 쓰는 자연어 표현 목록(6.1)
    -- 'both'는 두 계열 모두에서 선택할 수 있는 항목
    applies_to TEXT NOT NULL DEFAULT 'both'
        CHECK (applies_to IN ('scene_family','flow_family','both')),
    label TEXT NOT NULL,
    natural_phrases TEXT[] NOT NULL DEFAULT '{}',
    runtime_ref TEXT,
    is_active BOOLEAN NOT NULL DEFAULT true,
    PRIMARY KEY (catalog_snapshot_id, entry_kind, entry_code)
);

CREATE TABLE artwork_versions (
    artwork_version_id UUID PRIMARY KEY,
    artwork_id UUID NOT NULL REFERENCES artworks(artwork_id),
    spec_id UUID NOT NULL,
    version_key TEXT NOT NULL UNIQUE
        CHECK (version_key ~ '^[A-Za-z0-9_-]{1,64}$'),
    build_state TEXT NOT NULL DEFAULT 'draft'
        CHECK (build_state IN
            ('draft','building','candidate','qa_rejected','approved')),
    bundle_key TEXT,
    bundle_sha256 TEXT CHECK (bundle_sha256 ~ '^[0-9a-f]{64}$'),
    frozen_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (artwork_id, spec_id)
        REFERENCES spec_revisions(artwork_id, spec_id),
    CHECK (build_state <> 'approved' OR
        (bundle_key IS NOT NULL AND length(btrim(bundle_key)) > 0
         AND bundle_sha256 IS NOT NULL AND frozen_at IS NOT NULL))
);

CREATE TABLE nodes (
    node_id TEXT PRIMARY KEY CHECK (length(btrim(node_id)) > 0),
    role TEXT NOT NULL CHECK (role IN ('production','show')),
    agent_session_id UUID NOT NULL,
    environment_fingerprint TEXT NOT NULL,
    schedulable BOOLEAN NOT NULL DEFAULT false,
    last_heartbeat_at TIMESTAMPTZ
);

CREATE TABLE jobs (
    job_id UUID PRIMARY KEY,
    artwork_version_id UUID NOT NULL
        REFERENCES artwork_versions(artwork_version_id),
    stage TEXT NOT NULL CHECK (stage IN
        ('plan','background','asset','preprocess','assemble','qa','publish')),
    state TEXT NOT NULL DEFAULT 'waiting'
        CHECK (state IN ('waiting','ready','running','retry_wait',
                        'succeeded','failed','cancelled','blocked')),
    idempotency_key TEXT NOT NULL UNIQUE
        CHECK (length(btrim(idempotency_key)) > 0),
    input_sha256 TEXT NOT NULL CHECK (input_sha256 ~ '^[0-9a-f]{64}$'),
    requires_ue BOOLEAN NOT NULL DEFAULT false,
    fencing_token BIGINT NOT NULL DEFAULT 0 CHECK (fencing_token >= 0),
    available_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE job_dependencies (
    job_id UUID NOT NULL REFERENCES jobs(job_id),
    depends_on_job_id UUID NOT NULL REFERENCES jobs(job_id),
    PRIMARY KEY (job_id, depends_on_job_id),
    CHECK (job_id <> depends_on_job_id)
);

CREATE TABLE job_attempts (
    attempt_id UUID PRIMARY KEY,
    job_id UUID NOT NULL REFERENCES jobs(job_id),
    attempt_no INTEGER NOT NULL CHECK (attempt_no > 0),
    worker_id TEXT NOT NULL CHECK (length(btrim(worker_id)) > 0),
    node_id TEXT REFERENCES nodes(node_id),
    agent_session_id UUID,
    fencing_token BIGINT NOT NULL CHECK (fencing_token > 0),
    requires_ue BOOLEAN NOT NULL,
    state TEXT NOT NULL CHECK (state IN
        ('leased','running','succeeded','failed','expired','cancelled')),
    lease_until TIMESTAMPTZ NOT NULL,
    heartbeat_at TIMESTAMPTZ,
    error_code TEXT,
    result_key TEXT,
    UNIQUE (job_id, attempt_no),
    UNIQUE (job_id, fencing_token),
    CHECK (NOT requires_ue OR
        (node_id IS NOT NULL AND agent_session_id IS NOT NULL))
);

CREATE UNIQUE INDEX one_active_attempt_per_job
    ON job_attempts(job_id) WHERE state IN ('leased','running');

CREATE UNIQUE INDEX one_active_ue_job_per_node
    ON job_attempts(node_id)
    WHERE requires_ue AND state IN ('leased','running');

CREATE INDEX jobs_ready_by_stage
    ON jobs(stage, available_at, created_at) WHERE state = 'ready';

CREATE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at := clock_timestamp();
    RETURN NEW;
END;
$$;

CREATE TRIGGER jobs_updated_at BEFORE UPDATE ON jobs
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
CREATE TRIGGER versions_updated_at BEFORE UPDATE ON artwork_versions
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

DDL과 함께 구현해야 할 서비스 규칙은 다음과 같다.

- 기획 작업은 먼저 저장한 입력 명세 초안·후보 버전에 연결하고, Head의 확정 결과는 새 불변 명세 리비전으로 남긴다. 후보가 동결되기 전 참조 변경은 트랜잭션으로 처리하고, 동결 이후 변경은 새 작품 버전으로 만든다.
- **작업 그래프는 계열에 따라 생성한다.** `flow_family` 작품에는 `asset` 단계 작업을 만들지 않고, `background` 단계 작업은 명세의 `content.background`가 채워졌을 때만 만든다. 단계 목록을 공유한다고 해서 모든 작품이 모든 단계를 거치는 것은 아니다.
- **계열별 필수 명세 항목과 허용 카탈로그 코드를 검증한다.** 선택한 계열에 속하지 않는 템플릿·반응·파라미터 코드는 거절한다. `CHECK`만으로 JSONB 내부 항목을 검증하지 않으므로 서비스에서 계열별 JSON Schema를 적용한다.
- `CHECK`와 상태 목록은 모든 전이를 검증하지 않는다. 선행 작업 완료, 의존성 순환 금지, 허용 상태 전이, 현재 명세·입력 해시와 호환 카탈로그는 서비스에서 검증한다.
- `requires_ue`는 작업 정의와 시도에 일치하게 복사하고, UE 작업은 제작 역할 노드에만 배정한다. Agent 신원·세션과 토큰도 검증한다. 계열은 UE 작업 배정 조건에 영향을 주지 않는다.
- 임대가 만료된 시도는 만료 처리 트랜잭션 후 재배정한다. 시간 경과만으로 부분 고유 인덱스의 활성 상태가 바뀌는 것은 아니다.
- 승인 전에도 검수 대상으로 동결한 번들의 내용을 바꾸지 않는다. 바뀐 파일은 새 후보 버전으로 만들고 새 해시로 검수한다. 이 불변성은 최종 DB 권한·서비스 규칙·저장소 공개 방식으로 구현한다.
- 팔레트는 역할·색 형식을 검증하고, 시간은 해당 정책에서 필요한 값에만 양수·단위를 검증한다. 작품 전체 재생 시간은 없으며, 반응 길이 `interactions[].duration_sec`는 비어 있어도 오류가 아니다. 흐름 계열에서는 이 칸이 막혀 있다. 필수 문자열은 NULL뿐 아니라 공백도 검사한다.
- 자산·검수·게시·관측 테이블과 승인 가드, 권한, 보존 정책은 최종 마이그레이션에 포함한다. 예제 DDL만 실행해 게시 안전성이 완성됐다고 보지 않는다.

작업 선택에는 `SELECT … FOR UPDATE SKIP LOCKED` 같은 짧은 잠금 방식을 사용할 수 있다. 이 방식의 선택·갱신·시도 생성은 하나의 트랜잭션으로 처리하고 노드의 단일 UE 제한도 함께 검사한다. 일반 조회에 무조건 적용하지 않는다. PostgreSQL은 큐 형태의 다중 소비자 접근을 이 옵션의 사용 사례로 설명한다. [행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html) · [SKIP LOCKED](https://www.postgresql.org/docs/current/sql-select.html) · [DB 제약 조건](https://www.postgresql.org/docs/current/ddl-constraints.html)

## 15. API와 운영 UI — 구현 제안

다음은 기능 경계를 정리한 제안이며 기존 저장소에서 이미 제공하는 API 목록이 아니다. URI·인증·이벤트 전달 방식은 구현 시 확정한다. 운영 앱과 Agent는 API에 접근하며 DB·브로커를 직접 공유하지 않는다.

| 기능 | 요청·응답에서 필요한 정보 |
|---|---|
| **카탈로그 조회** | 현재 스냅샷의 계열·템플릿·스타일·매질·운동 규칙·입력·반응과 허용 조합 |
| 작품 요청·수정본 제출 | 프로젝트·**계열**·원문·명시 조건·모드·멱등 키 → 작품 ID·명세 리비전·접수 상태 |
| 작품·작업 조회 | 작품·계열·버전·작업·시도·단계·실패 사유·중간 산출물 |
| 노드 등록·heartbeat | 노드·Agent 세션·호환 환경·자원·UE 상태·현재 작업 |
| 작업 임대·갱신 | 가용 노드·능력 → 작업·시도·소유권 토큰·입력 참조·임대 만료 |
| 진행·결과 보고 | 시도·토큰·입력 해시·완료 결과·증거 → 채택/중복/거절 |
| 자산 업로드·다운로드 | 권한 있는 자산 ID·시도별 경로·해시·완결성 |
| 시연 명령·상태 보고 | 게시 명령·대상 버전·순서, 준비·적용 결과, 실제 활성 세션·버전 |
| 예외 제어 | 취소·보류·재시도·복구 요청과 요청자·사유·감사 기록 |

운영 UI는 계열을 선택한 뒤에 해당 계열의 카탈로그 항목만 보여준다. 선택 가능한 표현·반응 목록을 계열과 무관하게 전부 노출하면 사용자가 성립하지 않는 조합을 고르게 된다.

30분 이상 걸리는 생성 작업은 HTTP 요청 하나를 열린 채 기다리는 구조로 만들지 않는다. 접수 후 작업 ID를 반환하고 UI는 진행 상태를 조회한다. 폴링·이벤트 구독 중 구체 방식은 미정이다. 재연결 시 마지막으로 확인한 이벤트 이후를 조회하거나 최신 스냅샷을 다시 받아 누락을 복원한다.

운영 화면은 작품 요청·명세, 제작 진행, 자산·미리보기, 노드 상태, 현재/다음 전시, 오류·재시도 영역으로 구성한다. 전체 완료율을 실제 측정 없이 정확한 숫자로 만들지 않고 단계·경과 시간·완료된 하위 작업 수를 우선 표시한다. 계열에 따라 단계 수가 다르므로 진행 표시를 계열별 단계 목록 기준으로 계산한다. 현재 전시 버전과 다음 준비 버전은 분리하고 Applied 관측 시에만 실제 적용 표시를 바꾼다.

Qt UI 메인 스레드에서 생성·다운로드·오래 걸리는 처리를 기다리지 않도록 한다. 로그 검색은 JSON 로그 + Alloy · Loki · Grafana 경로와 연결하되, 작업 상태의 기준을 로그로 대체하지 않는다. 공통 ID·단계·오류 코드를 기록하고 공급자 비밀 키와 민감한 인증 정보를 로그에 넣지 않는다.

## 16. 외부 AI·전처리·비용 관리

| 역할 | 설계 | 계열 |
|---|---|---|
| Head·명세 작성 | 지원 카탈로그와 계열별 명세 규격을 입력으로 사용. 모델·프롬프트 버전 기록 | 공통 |
| 배경 생성 | 이미지·영상 공급자 어댑터, 배경 준비 완료 후 다음 단계 해제 | 장면 |
| 시각 에셋 생성 | 해당 작품 배경·팔레트·재질·역할을 참조해 생성 | 장면 |
| 전처리 | 필요한 규격 변환·마스크·반응 영역·흐름 데이터 생성 | 주로 장면 |
| 깊이·레이어 처리 | 선택한 표현이 요구할 때 사용. 알파·깊이·실제 3D 지오메트리를 구분 | 장면 |
| 사용량 관리 | 공급자 작업 ID, 호출 상태, 시간, 이미지·영상·토큰 등 과금 단위, 실제 비용·통화·미확인 상태 기록 | 공통 |

흐름 계열은 기획 단계와, `content.background`가 채워진 경우의 배경 생성 외에는 외부 공급자 호출이 발생하지 않는다. 작품별 예산 관리에서 두 계열의 비용 구조가 다르다는 점을 반영하고, 평균 비용을 계열 구분 없이 산출하지 않는다.

배경과 에셋은 역할을 분리하지만 서로 다른 공급자를 반드시 써야 하는 것은 아니다. 라넬이 확보한 도구의 실제 API 호출·결과 조회·자동화 권한을 확인한 뒤 선택한다. 기획 모델도 확정 전이며 첨부안의 모델명·가격·GPU 수치를 확정 스택이나 장비 기준으로 옮기지 않는다.

공급자 장애·시간 초과에서는 기존 작업을 조회하고 재시도 여부를 판단한다. 명확한 거절·잘못된 입력·권한 문제와 일시 장애를 구분한다. 공급자별 제한과 작품별 예산을 설정해 무한 재생성·무제한 대기를 막는다. 비용을 모르면 0으로 기록하지 않고 미확인으로 남긴다.

로컬 추론을 추가할 경우 정확한 체크포인트·라이선스·GPU·정밀도·해상도·오프로딩 조건을 검증한다. 제작 노드에서 UE와 자원을 공유하면 같은 장비의 자원 배정을 조정한다. 시연이 진행 중이라는 이유로 다른 제작 장비의 생성을 중단하지 않는다.

## 17. LGPL 이용과 프로토타입 전달

사용자는 PySide6 + Qt Widgets를 LGPLv3 조건으로 이용하기로 결정했다. 운영 앱 고유 소스를 비공개로 유지하는 방향이며, LGPL 적용 라이브러리의 대응 소스 제공과 구분한다. Qt도 조건을 충족한 라이브러리 이용 프로그램의 비공개 경로를 안내한다. [Qt 공식 LGPL 안내](https://www.qt.io/development/open-source-lgpl-obligations)

실제 Qt/PySide 버전·포함 모듈을 고정하고 라이선스 고지·대응 소스·호환 수정 라이브러리 교체를 검증한다. 추가 Qt 모듈·코덱·모델·자산은 각각의 조건을 확인한다. PySide6 선택이 이들의 조건을 대신하지 않는다. 기업에 라이브러리를 포함한 앱 복사본을 전달하는 시점부터 기존 [무료 배포 체크리스트](./pyside6-distribution-checklist.md)를 적용하며, 상업 출시까지 이 작업을 미루지 않는다.

2026-10-19 GitLab 확인 시 [AGENTS.md](../../AGENTS.md)와 [THIRD_PARTY.md](../THIRD_PARTY.md)에 MIT·Apache·BSD 계열만 허용하고 GPL 계열을 제한하는 규칙이 실제로 있었다. 기존에 멘토 발언으로만 알고 있던 내용과 구분해 기록한다. 사용자의 LGPL 선택은 유지하되, 저장소 규칙의 적용 범위·예외와의 정합성은 별도로 확인해야 한다. 선택을 회사 정책 승인이나 배포본 준수 검증으로 표시하지 않는다. [정합성 검토 항목](./README.md#라이선스-정합성)을 따른다.

| 1 | 공통 실행기·계열 구분이 있는 카탈로그·자산 계약과 PostgreSQL 기본 모델 | 정상/미지원 명세와 자산을 구분하고 이력을 저장 |
| 2 | **흐름 계열** 경로: PySide6 → FastAPI → 큐·스케줄러 → 제작 Agent 1대 | **외부 공급자 없이** 작품 한 건의 기획·조립·단계·진행·재시도 확인 |
| 3 | 자동 검수 → 번들 전달 → 독립 시연 PC 적용 | A 상영 중 B 제작·준비·Applied 확인, 실패 시 A 유지 |
| 4 | **장면 계열** 경로 추가: 배경·에셋 생성·전처리 단계 | 모의 공급자·샘플 자산으로 의존성과 부분 재시도 확인 |
| 5 | 제작 Agent 2대와 공통 조립 큐 | 서로 다른 계열의 작품 병렬 제작, 중복 임대·늦은 결과·노드당 UE 제한 확인 |
| 6 | 공급자 실제 연동과 계열별 품질·성능 검사 | 비용·시간·규격·조합·반응·복귀·장시간 안정성 기준 확인 |
| 7 | 명시적 준비·교체 어댑터와 반복 운영 | 선택한 제어 방식의 요청·결과·복구 일관성, 실제 장비 반복 시험 |
| 8 | 같은 조건의 N대 확장·프로토타입 인계 | 호환 노드 등록, 용량·로그·복구·배포 자료 확인 |

**흐름 계열을 먼저 통합 시험에 사용한다.** 외부 공급자·자산 생성 의존이 없어 공급자 선정 전에도 기획부터 게시까지 전체 경로를 실제로 돌릴 수 있고, 생성 실패 경로가 없어 골격의 문제와 생성의 문제를 분리해 관찰할 수 있기 때문이다. 이 순서는 장면 계열의 우선순위를 낮추는 결정이 아니며, 공통 경로가 검증된 뒤 생성 단계를 끼워 넣는 방식이다.

다만 3.4의 흐름 계열 실행기 확인 항목이 해결되지 않으면 이 순서를 적용할 수 없다. 확인 결과에 따라 장면 계열을 먼저 통합 시험하는 경로로 되돌릴 수 있도록 단계 1의 카탈로그·모델 작업은 두 계열을 함께 설계한다.

초기 통합 시험을 한 제작 노드로 시작하는 것은 운영 목표를 단일 제작 PC로 바꾸는 결정이 아니다. 시연 장비와의 분리는 첫 전체 경로 시험부터 유지한다. 외부 생성 모델을 아직 정하지 않았어도 모의 응답과 샘플 자산으로 이 경계를 구현할 수 있다.

완료 확인에는 다음 사례를 포함한다.

- [ ] 사용자가 선택한 계열이 명세·작업 그래프·카탈로그 선택지에 일관되게 적용된다.
- [ ] 흐름 계열 작품에 배경·에셋 생성 작업이 생성되지 않는다.
- [ ] 선택한 계열에 속하지 않는 템플릿·반응·파라미터 코드가 거절된다.
- [ ] 계열과 원문이 불일치할 때 Head가 계열을 임의 변경하지 않고 보류한다.
- [ ] 같은 명세·카탈로그 기준으로 제작 노드들이 서로 다른 계열의 작품을 처리한다.
- [ ] 노드당 UE 최대 1개를 지키고 에디터·별도 검증 실행본이 겹치지 않는다.
- [ ] 배경 준비와 에셋 생성의 의존성이 지켜지고 다른 작품은 병행한다.
- [ ] 작업 임대 만료·중복 메시지·늦은 결과·Agent 재시작이 승인 결과를 오염시키지 않는다.
- [ ] 계열별 필수 검수 항목과 원인별 재작업이 동작한다.
- [ ] 흐름 계열의 거동·장시간 안정성 검사가 짧은 프리뷰만으로 통과 처리되지 않는다.
- [ ] 자동 검수 통과 후 작품별 사람 승인 없이 게시가 진행된다.
- [ ] 자동 제작은 원문 제출 후 사람 확인·보정 없이 기획까지 진행되고, 실행기 숫자는 LLM이 아니라 카탈로그 대응표로 정해진다.
- [ ] 편집 제작 모드는 AI가 채운 명세 전체를 보여 주고, 운영자가 고친 값은 `user_explicit`로 기록되며 Head가 덮어쓰지 않는다. 필수 칸은 `"none"`으로 비울 수 없고, 막힌 칸은 `null`로 고정된다.
- [ ] 확신이 낮은 목록 칸은 억지로 매칭하지 않고 자동 제작이 멈추지 않으며, 못 맞춘 구절이 `unmatched_phrases`로 생성 단계까지 전달된다.
- [ ] 현재 작품 실행과 다음 작품 준비가 분리되고 실패 후보가 현재 작품을 중단시키지 않는다.
- [ ] 계열이 다른 작품 사이의 교체에서 이전 상태가 다음 작품에 남지 않는다.
- [ ] Ready와 Applied를 구분하고 현재 세션의 실제 활성 버전으로 적용 완료를 확인한다.
- [ ] 앱 종료·중앙 통신 단절·외부 AI 지연 중 현재 작품과 현장 손 입력이 유지된다.
- [ ] 통신 복구·UE 재시작 시 오래된 상태 파일을 새 적용 결과로 오인하지 않는다.
- [ ] 승인 번들 불변성과 현재·준비 중·마지막 정상 작품의 캐시 보호가 유지된다.
- [ ] 실제 Qt 배포본의 고지·대응 소스·교체 절차를 검증했다.

무중단 전환은 목표이며, 프레임 저하·메모리·미디어 준비·반복 교체를 실제 장비에서 측정하기 전까지 성능 검증 완료로 표시하지 않는다.

## 19. 남은 결정과 원본에서 반영한 변경

| 미정 항목 | 결정에 필요한 정보 |
|---|---|
| **흐름 계열 실행기 계약** | 3.4의 확인 항목. 자산·파라미터 형식, 손 입력 연결, 지속 실행 성능 || **카탈로그 값의 구현 범위** | 6.1 값 중 실제 실행기에 구현되는 코드와 허용 범위. `emerge`·`light`·`direct` 등은 아직 실행기에 없음 |
| **매질과 반응이 다른 표현 방식을 가리킬 때** | 예: 매질 `particle`(입자)인데 반응 `follow`(군집에서만 됨). 어느 쪽을 따를지, 한 작품에 표현 방식 두 개를 허용할지. 결정 전까지 6.2 보류 대상에서 제외 |
| **평상시 움직임에 맞는 값이 없을 때** | 예: "헤엄침", "쏟아짐". 반응 목록에 없어 흐름 계열의 필수 칸이 엉뚱한 값으로 바뀔 수 있음. `fall`·`drift` 같은 평상시 전용 값을 더할지. 1.3부터 확신이 낮으면 억지로 바꾸지 않지만, 흐름 계열에서는 필수 칸이라 Head가 다른 값을 골라야 함 |
| **매칭 확신도 기준** | `confidence`의 `high`·`low`를 가르는 방법(LLM 자기 평가·임베딩 유사도 등)과 기준값. 대표 문장으로 시험해 정함 |
| **원문 해석을 두 단계로 나눌지** | 1단계 칸별 구절 나누기, 2단계 코드 매칭. 목록이 자주 바뀌면 2단계만 다시 돌릴 수 있지만 호출이 한 번 늘어남. 1.3은 한 번의 호출에서 구절과 코드를 함께 출력함 |
| `space`·`asset_roles` 정리 확인 | 3.3에서 `space`를 `composition`에 합치고 `asset_roles`를 템플릿 계약 값으로 뺀 판단이 맞는지 |
| **계열별 검수 임계값** | 흐름 계열 관찰 시간, 장시간 안정성 판정 기준 |
| EC2 사양·저장공간 | 인스턴스 타입, 메모리, 볼륨 크기, 증설 가능 여부 |
| 자산 저장소 운영 설정·보존 정책 | 생성 PC 전용 디스크·SMB 배치는 확정. 실제 경로·계정·권한·용량·대역폭·백업·복구·보관 정책 확인 |
| 기획·이미지·영상 공급자 및 모델 | 라넬 계정·API 권한·출력 품질·시간·가격·자동화·이용 조건 |
| EC2 OS·배포 방식·백업 | SSAFY 제공 범위, Celery 지원 환경, 운영·과제 종료 후 인수인계 |
| 정확한 카탈로그·실행기 빌드·목표 PC 예산 | 기존 UE/TD 담당이 제공하는 버전·지원 조합·장비 실측 |
| 원격 Prepare/Commit 어댑터 | UE 내부 API와 외부 제어 계약, 명령 순서·취소·상태 보고 방식 |
| 로그인·Agent 인증·진행 갱신 방식 | 접근 주체·권한·네트워크와 운영 UI 요구 |
| 대기/재시도·큐 상한 | 대표 작품 시험, 공급자 한도·예산, 장시간 운영 결과 |
| 실제 패키저·모듈·라이브러리 버전 | LGPL 배포 방식과 교체 시험 결과 |
| SQLite 추가 여부 | 실제로 필요한 로컬 초안·조회·복구 기록의 규모. 초기에는 추가하지 않음 |
| 계열 추가 가능성 | 데이터 반응형·사운드 반응형 등 추가 요구가 생길 경우의 카탈로그 확장 |

| 첨부안에서 유지한 장점 | 분산형으로 조정한 내용 |
|---|---|
| 자유 입력과 구조화된 확인 화면 | 자동 제작은 확인 없이 기획·게시까지 진행. 편집 제작 모드에서는 AI가 채운 명세 전체를 운영자가 편집한 뒤 제출. 칸마다 출처·원문 구절을 함께 보여 줌 (1.4) |
| 원문·추출 근거·매핑·사용자 수정 기록 | 불변 명세 리비전과 Head 선택 출처를 추가 |
| 팔레트·입력과 반응 분리 | 실제 기능 카탈로그·허용 조합·장비·버전 검증과 연결 |
| **무대형/시스템형 작품 구분** | **고정 2종 타입 대신 템플릿 카탈로그의 두 계열로 편입. 계열은 템플릿의 속성이며 추가 가능** |
| **타입 선택 라디오 버튼** | **계열 선택으로 유지. 자동 모드에서는 운영 정책이 결정** |
| **타입별 파라미터 테이블 분리** | **한 스키마의 칸을 `spec` JSONB에 두고, 계열별 칸 상태(필수·선택·막힘)를 JSON Schema로 검증 (1.2)** |
| AssetStore·해시·썸네일·재사용 참조 | 공유 저장·전달·불변 번들·노드별 캐시와 보호 정책으로 확장 |
| 단계별 결과 보존과 재시도 | 중앙 작업·시도·임대·소유권 토큰·재작업 경로로 구체화 |
| 고정 공통 코드 + 데이터 | 새 범용 Spawner 대신 기존 ArtworkSceneHost·scene/release/status 계약 재사용 |
| 실패 시 기존 작품 유지 | 독립 시연 노드, 준비/활성 상태 분리, 마지막 정상 작품·재연결 대조로 구현 |

원본의 SQLite 중심 저장·동일 PC 가정·모든 작품의 수동 확인·같은 작품 배경/에셋의 무조건 병렬화는 위 설계로 교체했다. 모델·GPU·용량의 미검증 수치, JSON 검사만으로 검수가 끝난다는 설명, 모든 깊이를 UE Z축에 바로 대응시키는 설명은 구현 기준에서 제외했다. 원본이 제안한 `viewpoints` 4종과 음성·접근·터치 입력은 현재 설치에서 검증되지 않았으므로 카탈로그 초기값에 넣지 않고 확장 후보로 둔다. 좌표·깊이·자산 형식은 실제 실행기 계약을 따른다.

1.1 개정에서 추가한 계열 분기는 원본의 작품 유형 구분을 수용한 것이며, 고정된 두 타입이 아니라 확장 가능한 분류로 편입했다. 흐름 계열의 실행기 지원은 사용자 확인에 따른 전제이며 이 문서에서 직접 검증하지 않았다.

## 근거와 검토 범위

기존 라넬 구현에 관한 내용은 2026-10-18에 확보한 `interactive-runtime` 커밋 `613e6a86ab04d3f87435557ef9186846fce88a8b`와 관련 저장소 감사 자료를 기준으로 했다. GitLab 게시 준비에서는 `develop`의 `ccd14e9e08cfe5088fef226f5bbb574639b6136a`를 대조했다. 이는 위 GitHub 런타임 기준 커밋과 다르다. GitHub 최신 코드를 다시 가져오거나 Qt·UE·공급자 API·PostgreSQL 운영 환경을 실행 시험한 것은 아니다. 1.1 개정에서 추가한 계열 분기는 설계 수준의 제안이며, 흐름 계열의 실행기 지원·자산 계약·성능은 확인하지 않았다. 예제 JSON과 DDL은 구조 설명용이며 실제 실행·동시성 시험 결과가 아니다. 실제 구현·배포·부하 시험은 별도로 수행할 확인 항목으로 남긴다.
