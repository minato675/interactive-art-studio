# UE 시나리오 감독

작품의 큰 현상에서 생성 파일, 화면에 놓을 개체, 관객 반응, 시간 흐름, 검수 근거까지 연결한다. 감독은 제작 프롬프트만 늘어놓지 않고 **왜 이 템플릿과 배경을 택했으며, 실제 배경의 어느 공간에 무엇을 몇 개 놓아 어떤 경험을 만드는지** 설명한다. 현재 지원하는 실행 계획과 앞으로 구현할 연출을 함께 보존하되 둘의 상태를 구분한다.

이 문서는 전체 감독 절차다. EC2 Head의 API 지침은 [head-director-prompt.md](head-director-prompt.md)를 사용한다. 스킬 파일을 수정했다는 사실은 실행 중인 Head에 반영됐다는 증거가 아니다. 서버의 프롬프트 로드·버전 기록·구조화 응답 검증·배포 연결을 별도로 확인한다. 스킬이나 명세만 수정하는 요청에서는 이미지 생성, 유료 API 호출, 제작 자동화 재개를 실행하지 않는다.

## 1. 작품의 의도와 실제 제작 범위를 정한다

한 문장으로 자연 현상과 관객의 기여를 정한다. 예를 들어 잎이 각각 반짝인다는 설명에서 끝내지 않고, 관객이 만든 국소 변화가 잎의 방향과 밀도를 통해 어떤 큰 흐름으로 읽히는지 적는다. 작품마다 소재·시점·색·가림·합류 형태를 선택하며 모든 작품을 같은 S자나 터널로 만들지 않는다.

현재 EARTH는 가로 12m × 세로 3m의 직선 LED 벽, 4:1 구도, 뎁스카메라, 실시간 반응과 비동기 AI 이미지·에셋 갱신을 지향한다. 참고 영상의 큐브·풍선·회랑은 질감·부피·국소 변형·스케일을 읽는 표현 자료다. 그 설치를 직선 벽의 실제 구조로 오인하거나 부적합한 참고로 버리지 않는다.

**현재 생성 조건의 1920 × 1080 및 실행 화면의 16:9 매핑과 목표 4:1은 해결할 제작 차이**다. 실제 입력 조건과 원본 치수를 보존하고, 출력 픽셀·카메라·유효 영역·크롭·분할·프로세서 매핑의 확정 여부를 기록한다. 16:9를 조용히 늘이거나 프롬프트에 4:1을 적은 것만으로 12m 화면 준비 완료를 선언하지 않는다. 구도 제안과 중간 시안은 진행할 수 있으며 최종 벽면 검수는 미검증으로 남긴다.

## 2. 생성 전에 실제 UE 템플릿을 확정한다

서버가 제공한 템플릿 목록, 슬롯, 버전·fingerprint, 온라인 제작 노드의 지원 보고, Spec을 읽는다. 표현이 비슷한 이름을 새 템플릿처럼 만들지 않는다. 현재 Head는 Spec의 반응·매질을 서버 정책으로 매핑하므로, 원하는 템플릿 이름을 문장이나 `template_ref`에 적는 것만으로 선택이 바뀌지 않는다. preflight가 반환한 선택이 제작 기준이다.

| 확인할 것 | 감독의 결정 |
|---|---|
| 실제 템플릿·설치 증거 | 선택 근거와 지원 노드를 확인한다. 설치 보고와 실제 화면 검증을 구분한다. |
| 배경의 사용 방식 | 화면 표시용 `display`, 변형할 바탕 `canvas`, 색·조명 참고용 `style_reference`를 구분한다. |
| 입력·행동·슬롯 | 반응, 표현 방식, 레이어, 입자·복귀 슬롯의 실제 허용 범위 안에서 실행 계획을 만든다. |
| 생성 조건 | 서버가 정한 파일 역할·이름·형식·알파·권장 크기를 생성 지시에 반영한다. |

현행 지원 예시는 `gpu_particles`, `image_stir`, `fluid`, `paint`, `deformation`이다. GPU 입자 장은 배경을 표시하고, 그림 휘젓기는 far 이미지를 캔버스로 쓰며, 유체·그리기·표면 변형은 불투명 캔버스가 뒤 배경을 가릴 수 있다. 서버의 최신 조건이 이 예시보다 우선한다. 따라가기·빛나기 등 한 반응이 가능하다는 이유로 모든 제스처, 다중 규칙, 임의 입자 시스템까지 지원한다고 해석하지 않는다.

핵심 경험이 지원 밖이면 그 차이를 제한과 추가 구현 항목에 남긴다. 사용할 수 있는 효과로 표현을 바꿀 때도 원래 의도가 어느 정도 유지되는지 설명한다. 전파·합류·잔류가 없는 템플릿을 단순 반짝임만으로 EARTH 경험 충족이라고 평가하지 않는다.

## 3. 배경을 먼저 기획하고 생성 결과를 관찰한다

배경은 전체 자연 현상의 큰 구조, 주색과 보조색, 광원, 시점, 깊이와 빈 통로를 만든다. 에셋이 들어갈 공간은 확보하되 넓은 검정 위에 작은 장식만 남기지 않는다. 중·앞 레이어나 향후 움직일 독립 객체를 배경 한 장에 구워 넣지 않는다. `style_reference`라면 생성한 풍경이 최종 화면에 그대로 보일 것처럼 계획하지 않는다.

배경 생성 지시는 선택한 템플릿과 확정 조건을 따른다. 아직 없는 에셋의 정확한 종류·수량·좌표를 이 단계에서 확정하지 않는다. 제작 가능성에 대한 초기 가설은 유지할 수 있지만 최종 결정은 실제 생성 배경을 본 뒤 한다.

배경 파일이 반환되면 실제 이미지를 열거나 API 이미지 입력으로 받아 다음을 관찰한다. 파일명·해시·실제 치수를 함께 보존하며 프롬프트에 쓴 내용과 이미지에 보이는 내용을 구분한다.

- **색과 빛:** 실제 주색·보조색, 밝은 면의 위치, 광원의 방향·부드러움, 그림자의 일관성.
- **공간:** 시점·수평선·후퇴 방향, 앞뒤 가림, 이미 채워진 영역과 에셋을 놓을 수 있는 영역.
- **배치 근거:** 화면 좌표로 설명할 빈 통로, 시선의 중심, 가려서는 안 될 질감·합류부, 움직임 여유.
- **결함과 한계:** 불필요한 글자·인물·로고, 반복 무늬, 잘린 형상, 비율 차이, 불분명한 깊이.

보이지 않는 영역이나 정지 이미지의 움직임을 관찰 사실로 만들지 않는다. 배경을 받지 못했으면 에셋 선정 전 단계에서 기다린다. 실제 배경이 의도와 크게 다르면 재작업 근거를 남기고 사용 가능한 재작업 절차로 돌린다. 현재 응답 스키마에 없는 승인·재시도 명령을 임의로 만들어 실행시키지 않는다.

## 4. 생성 원본과 화면 인스턴스를 따로 설계한다

**원본 에셋은 생성할 파일이고 인스턴스는 그 파일을 화면에 사용하는 개체다.** 동일 잎 이미지 한 장을 다섯 위치에 놓으면 원본 1개·인스턴스 5개다. 서로 다른 실루엣이나 면 방향을 가진 잎 세 장을 만들면 원본 3개이며 각 파일을 재사용할 수 있다. 이미지의 명암을 바꾸려면 새 변형 원본이 필요한지, 실제 런타임이 지원하는 조절인지 구분한다.

실제 배경의 관찰 결과에 따라 원본마다 용도·형상·재질·빛·알파·크기와 생성 프롬프트를 정한다. 정면에서 읽을 꽃잎, 얇은 측면 잎, 합류부를 연결할 작은 물결처럼 역할이 구체적이어야 한다. 현재 2.5D 원본도 평면 RGBA 스프라이트다. 메시·리그·측정 깊이·여러 시점 파일을 확보했다고 쓰지 않는다.

인스턴스마다 고유 ID, 참조 원본의 1부터 시작하는 인덱스, 역할, 목적, `(u, v, size)`를 정한다. 인스턴스 ID는 `leaf_01`처럼 영문 소문자로 시작하는 소문자·숫자·밑줄 조합, 최대 48자로 만든다. 인스턴스와 모든 연출 기록의 ID는 대소문자 구분 없이 서로 달라야 하며 예약어 `background`를 쓰지 않는다. `(0, 0)`은 화면 왼쪽 위이고 `size`는 화면 너비에 대한 가로 비율이다. 같은 원본의 복제는 서로 다른 ID·위치·크기로 표현한다. 각각을 새 생성 작업으로 중복 계산하지 않는다. 정확한 수량은 원본별 사용 수와 전체 인스턴스 수로 확인한다.

현행 감독 계약은 원본 최대 12개·화면 인스턴스 최대 12개이며 모든 원본을 한 번 이상 사용한다. 요청이 원본 수를 명시하면 그 수를 지키고, 미지정이면 목적에 필요한 수를 예산 안에서 정한다. 12개 복제를 수만 개 GPU 입자와 혼동하지 않는다. 반복 규칙을 설명하더라도 실제 배치할 모든 인스턴스 좌표를 낸다. 에셋의 가로세로 비율과 이동 범위를 고려해 잘림·과밀·겹침을 검토한다.

## 5. 일부 개체의 반응과 효과를 구체화한다

전체 중 어떤 인스턴스가 관객에게 반응하는지 ID로 지정한다. `noninteractive`는 관객 반응이 없는 역할이고 `interactor`는 실제 반응을 담당하는 역할이다. 지원 조건이 허용하면 비반응 개체의 자율 float는 가능하다. 모든 개체에 같은 행동을 붙이지 말고 자율 구조를 유지하는 개체와 관객 입력을 드러내는 개체의 이유를 적는다.

실행 행동은 선택한 preflight의 `behaviors` 부분집합 또는 빈 목록이다. 선택에 follow/glow가 요구되면 적어도 한 인스턴스가 그 행동을 가진다. 하위 엔진에 어떤 이름이 있다고 현재 Head의 허용 행동을 늘리지 않는다. 효과·상호작용의 대상 ID는 실제 인스턴스와 연결한다.

`template_driven`은 현재 템플릿과 전달 메타데이터로 표현할 수 있는 **계획**이며 이미 적용·관찰됐다는 뜻이 아니다. `design_only`는 별도 구현이 필요한 연출 의도다. 현재 효과의 실행 표시는 glow 행동을 가진 개체의 glow, 상호작용의 실행 표시는 실제 입력 조건과 일치하는 follow/glow에 한정한다. 회전·색조 변화·개별 깊이·잔상·새 파문·메시 변형 등을 설명할 수 있으나 해당 구현 근거 없이 실행된다고 쓰지 않는다.

## 6. 입자와 시간 흐름을 작품의 구조로 연결한다

입자는 장식 분진의 기본 추가 항목이 아니다. 소재를 무엇으로 읽게 하는지, 어느 영역에서 발생하고 어떻게 이동·확산·합류하며 무엇을 남기는지 정한다. 원본 스프라이트의 복제 수와 입자 시스템의 수량·밀도를 따로 기록한다.

실제 입자 수와 반경·복귀는 제공된 Spec 및 서버 슬롯을 근거로 쓴다. 현행 감독 계약에서 GPU 입자의 `template_driven` 계획은 전역 입자장만 표현한다. 개별 에셋에 연결하는 방출기는 없으므로 target_ids는 빈 배열로, count·lifetime_seconds·speed는 null로 두고 서버 값을 따른다. 이미지 프롬프트나 감독 설명에 적은 임의 수량·수명·속도·힘이 엔진에 적용되지는 않는다. 다른 템플릿의 별도 입자나 새 수치 조절은 `design_only`로 남긴다.

시간 큐는 자율 상태 → 국소 시작 → 확산 → 합류 → 잔류 → 느린 복귀가 관객에게 어떻게 보이는지 설명한다. 숫자를 제안하면 연출 목표이며 실제 측정값과 구분한다. 현재 감독 큐는 `design_only`이고 타임라인 실행기가 자동 재생하지 않는다. 핵심 연결이 미구현이면 제한과 검수 항목에 드러내며, 기획서의 2초·5초 예시를 모든 작품의 고정 타이머로 만들지 않는다.

## 7. 완성 시나리오와 검수 근거를 인계한다

API에서는 제공된 스키마로만 응답한다. 신규 감독 흐름의 에셋 계획에는 감독 내용을 채우며 레거시 호환을 위한 선택 필드를 새 흐름에서 생략하지 않는다. 읽기용 시나리오는 다음 내용이 하나의 제작 의도로 이어지게 쓴다.

1. 제목·핵심 경험·선택한 실제 템플릿과 이유.
2. 실제 배경 관찰과 에셋 선정·배치의 근거.
3. 생성 원본 목록과 변형의 차이, 원본별 복제 수와 모든 배치.
4. 반응하는 인스턴스의 부분집합, 효과·입력·입자·시간 큐와 실행 상태.
5. 추가 구현 항목, 출력 매핑 차이, 실제 검수에 사용할 수용 기준.

정지 검수는 색·구도·재질·알파·반복·가림을, 실행 검수는 입력 인과·움직임·합류·잔류·복귀를 본다. 실제 센서와 현장 LED·장시간 운영은 각각 별도 증거가 필요하다. 기술 검증 결과와 배경·실행 캡처를 함께 읽고 `approve`, 소재 재작업, 배경 재작업, `hold` 중 현재 스키마가 허용하는 판단을 선택한다. 기술 실패나 환경 의심을 시각적 만족으로 덮지 않는다.

각 수용 기준에는 확인할 장면과 필요한 증거를 적는다. 예를 들어 “선정한 interactor만 입력 위치에 반응하고 나머지 구조는 유지된다”, “복제 위치가 배경의 주요 형태를 가리지 않는다”, “입력이 끝난 뒤 잔류가 관찰된다”처럼 쓴다. 증거가 없으면 미검증이며 정지 시안 점수만으로 전시 완료를 선언하지 않는다. 프롬프트 버전·템플릿 fingerprint·배경 해시·계획·관찰·수정 사유를 연결해 다음 제작자가 판단을 추적하게 한다.

## 에셋 수량과 생성 작업의 일치

asset_count가 null이면 실제 배경을 보고 0~max_asset_count에서 필요한 원본 수를 정한다. 대표 생성 조건 한 개는 원본 한 개를 반드시 만들라는 지시가 아니다. asset_count=0은 배경만 사용하라는 명시적 요청이며, 양수 지정은 정확히 지킨다. 독립 객체가 불필요하면 assets=[]와 director.instances=[]로 응답한다. 생성하지 않을 보류 원본·형식상 참조·숨김용 가짜 객체를 목록에 넣지 않는다. assets에 넣은 모든 항목은 실제 생성기로 전달되어 PNG가 필요하다. 빈 목록일 때 배경 canvas의 상호작용은 계속 설계하고, 별도 객체·원본·인스턴스를 만들었다고 쓰지 않는다.
