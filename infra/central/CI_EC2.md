# GitLab CI → EC2 소스 배포

CI의 코드·테스트·이미지 기동 검사가 성공하면 보호된 develop을 운영 443에 자동 배포합니다.
테스트 8444 배포 job은 제거합니다. main은 이 전환에서 변경하거나 배포하지 않습니다.
GitLab은 해당 커밋의 추적 소스만 SSH로 전달하고, EC2가 이 폴더의 Dockerfile·Compose로 빌드·실행합니다.
이미지 Registry나 이미지 tar 업로드는 사용하지 않습니다. CI와 EC2는 같은 커밋을 각각 빌드하므로
빌드 캐시·기반 이미지 갱신에 따라 이미지 ID는 달라질 수 있습니다. EC2에서도 설치 리소스·실제 비동기 완료를 검사합니다.

## 서버의 경로와 보존 대상

- `/opt/ranel/releases/<커밋 SHA>/`: 전달된 소스. 운영 비밀 파일을 소스 압축에 넣지 않습니다.
- `/opt/ranel/.env.infra`·`.env.https`·선택 `.env.head`: 서버 전용 설정. CI가 발급·덮어쓰기 하지 않습니다.
- 서버별 `compose.host.yaml`: PostgreSQL 최초 초기화 SQL을 고정 경로로 연결합니다.
  커밋 소스 폴더가 바뀔 때 초기화 SQL의 마운트 경로만 달라져 DB 컨테이너가 재생성되는 일을 피합니다.
- `/opt/ranel/current-image`·`current-release`: 마지막 성공 이미지와 Compose 위치.
- `/opt/ranel/current`: 마지막 성공 소스를 가리키는 링크. 최초 수동 설치 소스는 루트에 보존합니다.
- Compose 프로젝트 `ranel`, 기존 DB·파일·CA 볼륨과 노드 토큰을 유지합니다.

폐기한 테스트 환경은 `/opt/ranel-staging`에 자료만 보존합니다. `RETIRED` 표식이 있는 배포 대상은
소스 수신과 배포 스크립트에서 거부합니다. 8444 서비스를 다시 시작하지 않습니다.
운영 환경은 `/opt/ranel`, `ranel`, 내부 API 18080, HTTPS **443**입니다. 초기 이관 당시의 8443과 구분합니다.
테스트 환경에 운영 DB 덤프·노드 토큰·유료 AI 설정을 복사하지 않습니다.

설정 검사·빌드가 실패하면 실행 중 서버를 바꾸지 않습니다. 서비스 교체 후 준비 상태·비동기 검사가
실패하면 직전 성공 **이미지와 Compose 구성**으로 복구를 시도하고 job을 실패 처리합니다.
DB 스키마 역변환·무중단 전환을 보장하지 않습니다. 실행 중 작업이 있으면 배포를 중단하며,
운영자는 작업 요청이 없는 점검 시간에 실행합니다. 이는 원자적인 작업 접수 차단 기능은 아닙니다.

## GitLab 설정

| 변수 | 형식 | 범위 |
|---|---|---|
| `SSH_PRIVATE_KEY` | File, 배포 전용 SSH 개인키 | Protected, ec2/* |
| `SSH_KNOWN_HOSTS` | File, 사전에 확인한 서버 호스트 공개키 | Protected, ec2/* |
| `EC2_HOST` | `k15a504.p.ssafy.io` | CI 기본값. 변경 가능 |
| `EC2_USER` | `ubuntu` | CI 기본값. 변경 가능 |
| `EC2_DEPLOY_ENABLED` | `true` | Protected, 전체 환경. rules 판정용 비밀 없는 플래그 |

기존 제공 PEM을 GitLab에 올리지 않고 배포용 키를 별도로 준비합니다. File 변수는 값 대신 파일 경로로
job에 제공됩니다. 여러 줄 SSH 키는 Masked 형식의 제약에 맞지 않을 수 있으므로 값을 출력하지 않으며,
보호된 브랜치·ec2/staging 및 ec2/production job에서만 제공합니다. 환경 변수의 값 확장은 끕니다.
근거: [GitLab CI/CD 변수](https://docs.gitlab.com/ci/variables/).

개발 MR은 검증만 수행합니다. 보호된 develop은 운영 자동 배포를 실행하며,
GitLab resource group과 서버 파일 잠금으로 배포를 직렬화합니다. UFW·SSH·공개 포트는 CI가 변경하지 않습니다.

최초 EC2 실행 버전은 `3b02e88`이었습니다. 2026-10-22 실제 CI 테스트 배포 검증 당시
운영은 별도 후속 작업의 `c18d2591`, 테스트는 develop 병합 커밋 `bed24509`였습니다.
main은 당시 초기 커밋 상태이므로 기능의 통합·배포 MR 없이 오래된 코드를 운영에 덮어쓰지 않습니다.
배포 경로의 격리 검증과 운영 서버의 실제 버전 교체는 검증 기록에서 구분합니다.

## 직접 테스트하는 방법

현재 접속은 `https://k15a504.p.ssafy.io`(443) 한 곳입니다. 8444는 종료되었습니다.
팀원 PC의 설치·CA·토큰 설정, 운영 앱 실행, 실제 적용 SHA와 비동기 완료 확인,
장애 대응은 [테스트·운영 접속 안내](../../docs/ENVIRONMENT_ACCESS.md)를 따릅니다.

소스 수신 검사기는 최초 서버 준비 때 관리 SSH 키로 `/opt/ranel/ci/receive_source.py`에 설치합니다.
검사 정책을 바꾸면 관리자가 이 파일을 갱신합니다. 수신 전에 미검증 압축 속 코드를 실행하지 않습니다.

## 검증 기록

- Windows pytest 262 통과, PostgreSQL 전용 5개 건너뜀. Ruff·uv lock 검사 통과.
- 소스 수신의 경로·링크·비밀 파일·체크섬·중복 릴리스 거부 검사 9개 통과.
- EC2 테스트 환경에서 실제 소스 빌드·설치 리소스·진단/초안 비동기 완료 확인.
- 최초 격리 검증에서 테스트 HTTPS 인증서·운영자 인증·무인증 401을 확인하고 당시 운영 3b02e88을 유지했습니다.
- 사용자 승인으로 CI 전용 키·고정 known_hosts를 Protected File 변수(ec2/*)로 등록하고 develop 자동 배포를 활성화했습니다.
- MR !37 병합 커밋 bed24509의 파이프라인 #236465에서 7개 job과 실제 EC2 테스트 배포가 성공했습니다.
  운영 c18d2591의 컨테이너·설정·볼륨, 테스트 DB·브로커 컨테이너·볼륨을 보존했습니다.
- 현재 운영 443·테스트 8444의 HTTPS·DB 준비·인증을 조회 확인했습니다. main 실제 운영 수동 릴리스 검증은 별도입니다.
- GitLab CI 결과·배포 키 연결·실제 CI 배포 결과는 [MR !37](https://lab.ssafy.com/s15-final/S15P31A504/-/merge_requests/37) 본문에서 확인합니다.
