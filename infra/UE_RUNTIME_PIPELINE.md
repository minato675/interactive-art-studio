# UE 조립·실행 검증·PC2 시연 연결

중앙 EC2는 조립 완료 후 `ue_verify` 작업을 자동 등록한다. PC1의 전용 실행기는 전체 번들을 해시 검증해 검수 폴더에 준비하고 `ue_runner.Runner.verify()`의 게시 콜백으로 release.json을 원자 교체한다. 조립과 검증은 별도 임대·시도·결과를 갖는다.

검증 작업의 실행 성공과 작품 판정은 다르다. `runtime-report.json`의 verdict는 pass/review/fail이다. 새 자동 Head 요청은 기술 pass·AI approve를 모두 충족하면 PC2 `ue_publish` 작업을 등록한다. 기존 수동 조립과 auto_publish=false 흐름은 운영자의 명시적 승인을 기다린다. review는 사람 검수자와 사유가 필요하며 fail은 승인할 수 없다. PC2는 승인된 조립 번들만 내려받는다. 기본 관측 모드는 기존 Shipping 실행본 하나의 PID를 지정하며 프로세스를 제어하지 않는다. 선택적인 [시연 프로세스 관리 모드](../apps/show_agent/LIFECYCLE.md)는 같은 전달 규약으로 자동 실행·명시적 정지·비정상 종료 복구를 제공한다.

PC2의 파일 준비는 Staged, 실제 런타임 Ready/Applied는 상태 파일의 버전·요청 ID·세션·프로세스와 실제 실행 여부를 확인해 보고한다. 독립 prepare/commit을 지원하지 않는 현행 런타임에서는 Ready를 인위적으로 만들지 않는다. 연결이 끊겨도 로컬 작품을 삭제하거나 포인터를 초기화하지 않는다.

## 데이터 보관

이번 HTTP 연결의 원본 보관소는 EC2다. PostgreSQL에는 작업·의존성·시도·파일 목록·검증 판정·승인 기록·노드 상태를, `ranel_central-data` 볼륨의 `/data/artifacts/objects`에는 배경·에셋·scene.json·검증 보고서·캡처를 SHA-256 기준으로 보관한다. RabbitMQ는 파일 보관소가 아니다.

PC1 검수 폴더와 PC2 시연 폴더에는 실행용 버전 사본과 release.json·상태 파일이 남는다. 생성 PC의 원본 작업 폴더도 유지된다. 기존 STORAGE.md의 SMB 배치는 별도 설계이며 이 HTTP 경로는 SMB를 요구하지 않는다. EC2 볼륨은 독립 백업이 아니므로 DB와 파일 볼륨을 함께 백업해야 한다. 자동 삭제·외부 장기 보관·보존 기간 정책은 아직 없다.

## 전제와 한계

PC1은 MR !33의 ue_assemble·ue_runner와 호환 Shipping 빌드를 설치해야 한다. 중앙 이미지는 해당 UE 모듈을 포함하지 않는다. PC2에도 같은 콘텐츠를 지원하는 Shipping 빌드를 별도로 설치한다. 키트에는 실행본·UE 소스·API 모델 키를 넣지 않는다. 실제 GPU 화면 검증은 PC1 담당자의 실행 후에만 완료된다.

## 연결과 재시도

자동 검증 대상 ID는 `ue-review-1`이다. 이번 키트와 중앙 등록을 함께 적용한다. 기존 완료 조립은 자동 소급 등록하지 않으며 필요한 경우 같은 작품·버전·카탈로그의 `ue_verify` 작업을 운영자가 등록한다. 새 조립은 완료와 검증 등록이 하나의 DB 트랜잭션이다.

검증 작업의 `status=succeeded`는 보고서를 받았다는 뜻이다. 반드시 `result.verdict`를 함께 읽는다. 화면 fail도 보고서 보존을 위해 실행 완료로 남기며 게시 승인을 거부한다. 다운로드·실행기·통신 오류는 작업 failed 또는 임대 만료로 남는다. 완료 응답 유실은 같은 시도의 저장된 완료 내용을 재전송한다. 실제 재검증은 새 request_id로 `ue_verify`를 등록한다.

PC2 게시 승인에는 검증 작업과 조립 작업을 선행 관계로 넣고 대상 노드 ID를 고정한다. 다른 시연 노드는 이 작업을 가져갈 수 없다. 현행 watcher는 포인터 변경 시 자동 준비·적용하므로 독립적인 중앙 Ready→Commit 프로토콜은 구현하지 않는다.
