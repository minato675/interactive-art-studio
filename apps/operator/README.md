# apps/operator — 운영 PC 앱 (Artomation)

`시연 관리`의 `로컬 아카이브`는 최근 28개의 고정 목록과 PC2 선택 재생/정지 요청을 제공한다. `공용 런타임`은 기존 검증 작품 목록을 유지한다. 미설치·미접속은 실행 확인 대기로 표시한다. [연결 안내](../../docs/NATIVE_ARCHIVE_PLAYBACK.md)를 참고한다.

작품 제작의 자동 모드는 `/infra/head/intakes`에 원문을 비동기 접수한다. 생성·조립·실행 검증·게시 단계는 중앙 Head가 진행하며,
화면은 접수 작업과 Head 흐름을 주기적으로 조회한다. UE 제작 노드의 템플릿 지문이 맞지 않으면 `waiting_ue`로 보존하고
조건이 충족되면 자동 재개한다. 편집 모드·개발용 동기 API는 기존 경로를 유지한다.
자동 모드의 최종 검수 선택은 `auto_publish=false`로 전달한다. 소재 중간 검수와 복수 표현 선택은 현재 분산 경로에서 거부하며
지원하지 않는 옵션을 조용히 무시하지 않는다. 원문과 요청 ID를 보존하여 응답 유실 재시도 시 중복 제작하지 않는다.

GitLab 소스를 받은 팀원은 루트 `Start-Operator.cmd`로 실행하고 ID·비밀번호로 로그인합니다. 계정 발급·실행·TLS 안내는 [계정 접속 안내](../../docs/OPERATOR_LOGIN.md)에 있습니다. 공개 CA는 앱에 포함하며 개인별 토큰·CA 설치는 필요하지 않습니다.

`시연 관리` 탭은 현재 시연·검증 작품 목록, 수동 적용 요청/Applied 추적, 순서·시간·반복의 중앙 저장을 제공합니다.
작품당 시연 시간은 기본 2분(120초)이며 공통 옵션으로 바꾸면 모든 작품에 같은 시간을 적용합니다.
밝은 공통 테마로 실제 재생·장비 상태를 먼저 표시하고 편집은 접을 수 있습니다. 저장/동기화/적용/재생과 지원 제어의 구분은 [사용법·범위](../../docs/SHOW_DASHBOARD.md)를 따릅니다.
검증 작품 검색·페이지 이동·다중 선택 추가·목록 제거, 자동 순환 켜기와 PC2 적용 revision/구간 시간 보고는 [실제 재생 연동](../../docs/SHOW_PLAYBACK.md)을 따릅니다.
`OPERATOR_SHOW_DASHBOARD=0`이면 탭을 숨깁니다. 기본값은 표시이며 기존 세 탭은 유지합니다.

운영자가 작품을 요청하고, 결과 · 진행 단계 · 기록을 보는 설치형 앱입니다(PySide6 + Qt Widgets). 앱 이름은 **Artomation**이고 창 제목에 표시됩니다. 아이콘은 `src/operator_app/assets/artomation.png`를 읽어 창과 작업 표시줄에 씁니다. 파일이 없으면 Qt 기본 아이콘으로 실행됩니다.
EC2의 테스트·운영 서버에 연결할 때는 [팀원 접속·테스트 안내](../../docs/ENVIRONMENT_ACCESS.md)를 따릅니다.
아래의 central 직접 실행은 로컬 개발용이며 EC2 접속에 필요하지 않습니다.

`운영 현황` 탭은 EC2 웹 관리자와 같은 `/infra` 조회 API로 작업 집계·노드·시연 상태·작업 상세·Head 판단을 표시합니다.
앱에 설정한 운영자 토큰을 사용하며 조회 전용입니다. 선택한 탭에서 5초마다 작업 스레드로 갱신합니다.
검색·상태 필터·200개 단위 페이지 이동을 제공하며 집계는 현재 페이지 기준입니다.
조회 실패 때는 마지막 수신 자료로 표시하고 시연 상태를 현재 Applied로 표시하지 않습니다.
401이면 자료를 지우고 자동 조회를 중지합니다. 일시 오류는 `조회 시작`으로 다시 연결하며 토큰을 변경했다면 환경 변수를 설정하고 앱을 재시작합니다.
재생 라이브러리·정책의 설계와 실제 연동 전 검증 범위는 [재생 스케줄러 설계](../../docs/architecture/library-scheduler.md)를 따릅니다.

`작품 피드백` 탭에서 현재 시연 정보와 관리자 유지/개선 의견을 관리합니다.
작성 대상을 고정해 작품 전환 중에도 다른 작품에 의견을 붙이지 않으며 중앙의 활성 의견은 다음 Head 기획의 참고 기억이 됩니다.
사용법·API·참고 중지·재학습과의 차이는 [작품 피드백](../../docs/ARTWORK_FEEDBACK.md)에 있습니다.

후보 생성 완료는 `prepared`, 기존 `published`는 과거 게시 기록으로 표시합니다. 두 상태 모두 실제 Ready·Applied를 뜻하지 않습니다. 실패 시 출력별 원인을 단계 목록에 표시합니다. 기록 새로고침 시 `/infra/nodes`의 시연 노드 보고를 따로 조회하여 요청·활성 버전과 Staged/Ready/Applied를 표시합니다. 연결 끊김·조회 실패는 미확인으로 표시합니다. 사용자 제작의 빈 주인공은 원문에서만 추출하며 테마 기본 주인공은 전시 모드에서만 선택합니다. [제작 정책](../../docs/refactoring/creation-policy.md)을 참고합니다.

일반 개발 서버의 제작·확정·검수 API를 그대로 사용합니다. 로컬 `both` 설정에서는 TD·UE별 후보 파일을 준비하며 `published`를 실제 전시 적용으로 해석하지 않습니다. [후속 개발 복원 기록](../../docs/refactoring/post-mr23-restoration.md)을 참고합니다.

- **실행 장비**: 운영 PC. 앱을 꺼도 central의 작업은 계속됩니다.
- **가져다 쓰는 것**: [contracts](../../packages/contracts/README.md)(요청 · 응답 모델)만 씁니다. central 코드를 import하지 않고 HTTP API로만 통신합니다.
- **설치 · 실행**: 운영 앱은 루트 기본 설치에 들어 있지 않습니다(다른 장비에 Qt를 깔지 않기 위해).
  ```bash
  uv sync --all-packages                      # 운영 앱 포함 설치
  uv run uvicorn central.main:app             # central (다른 터미널)
  uv run a504-operator                        # 운영 앱. CENTRAL_URL · OPERATOR_TOKEN 환경 변수로 주소 · 토큰 지정
  ```
- **목표 명세와의 차이**: 설계 문서 1.4의 편집 제작은 작품 명세(`contracts.spec`, `content`·`idle`·`interactions`, 선택 칸 `"none"`·막힌 칸 `null`) 전체를 편집하는 방식입니다. 지금 앱은 central이 쓰는 요청 형식(`CreateRequest`)의 칸(아래 편집 칸)만 고칩니다. 편집 대상은 **명세의 막히지 않은 모든 칸**으로 결정했으므로(S15P31A504-165), central이 명세 형식으로 옮겨 가면 편집 폼도 명세 칸 전체로 바꿉니다(S15P31A504-168). 규칙은 [분산형 설계](../../docs/architecture/distributed-system-design.md)의 3.3절(칸 상태)과 5절(모드)에 있습니다.

| 파일 (`src/operator_app/`) | 내용 |
|---|---|
| `client.py` | central API 클라이언트 (작품 만들기 · 초안 · 확정 · 기록 · 표현 방식 목록) |
| `window.py` | 창. 모드 전환 · 요청 · 편집 초안 폼 · 사람 검수 카드 · 진행 단계 · 기록 · 전시 모드 |
| `monitor.py` | 운영 현황 탭. 노드·작업·Head 조회, 오프라인·오래된 보고 표시, 페이지·검색·작업 상세 |
| `feedback.py` | 작품 피드백 탭. 시연 정보·작성 대상 고정·의견 저장·참고 중지/재개·연결 실패 시 초안 유지 |

| `assets/artomation.png` | 앱 아이콘 |

## 모드 (Shift+Tab으로 전환)

| 모드 | 동작 | API |
|---|---|---|
| 자동 | 원문을 중앙 작업함에 접수하고 분산 제작·검증·게시 상태를 조회 | `POST /infra/head/intakes` → 작업·Head 조회 |
| 편집 | AI가 먼저 채운 초안을 폼에 보여 줌(AI가 채운 칸은 보라색 "AI 제안"). 필요한 칸만 고쳐 "이 내용으로 진행"을 누르면 **바꾼 칸만** 보냄. 맞지 않는 값이면 central이 거절하고 초안은 계속 기다림 | `POST /api/drafts` → `POST /api/artworks/{id}/confirm` |

- 편집 칸: 제목 · 표현 방식(1~3개) · 보이지 않는 주인공 · 드러내는 방식 · 분위기 · 색 · 반응 세기.
- 확정 때 central은 플래너를 다시 부르지 않아 초안에서 본 값이 그대로 결과가 됩니다. 사용자가 바꾼 칸만 `user_explicit`로 기록됩니다.
- **사람 검수(체크박스 2개, 기본 꺼짐)**: 자동 모드의 「최종 검수」는 PC1 검증 후 PC2 게시 승인을 기다리게 합니다. 자동 모드의 「소재 검수」는 아직 지원하지 않아 제출 시 안내합니다. 편집 모드와 기존 작품 기록에서는 소재 썸네일·개발 검수 폴더·승인/반려 카드를 유지합니다. 기술 판정 `review`는 선택 여부와 관계없이 사람 검수로 보냅니다.
- **전시 모드(체크박스)**: central의 [전시 자동 순환](../../infra/HEAD_EXHIBITION_FEED.md)을 켜고 끕니다(`PUT /infra/exhibition/feed`). 순환은 중앙 서버에서 돌기 때문에 앱을 꺼도 계속됩니다. 앱을 켤 때와 기록을 새로 고칠 때 `GET /infra/exhibition/feed`로 상태를 읽어 체크박스와 "켜짐 · 진행 중 n/10" · "쉬는 중(이유)"으로 보여 줍니다. 요청에 실패하면 체크박스를 서버 상태로 되돌립니다. 소재 · 최종 검수 체크박스는 운영자가 직접 제출하는 요청에만 쓰이므로 전시 모드와 무관하게 쓸 수 있습니다.

API 호출은 작업 스레드에서 하고 결과만 화면 스레드로 넘깁니다(생성이 오래 걸려도 창이 멈추지 않음).

화면은 요청 카드와 결과 카드로 나뉩니다. 진행 단계에는 짧은 한국어 요약을 보여 주고(`작품 명세` 단계는 Input Agent의 판단), 전체 응답 JSON은 오른쪽의 `원본 데이터 보기`를 펼쳐 확인할 수 있습니다. 작품 기록은 최신 작품부터 표시합니다.
